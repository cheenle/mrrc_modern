# 下一版（backlog）

> 记录"已经想清楚、只差做"的东西。每条都带**验收标准**——没有验收标准的条目只是愿望。

## 1. 应用内一键：接入 / 升级 / 打补丁

**背景**（2026-10-03）。今天把三件事做成了"下载一个 `.cmd`、双击"：
`MRRC-Modern-Connect.cmd`、`MRRC-Modern-Patch.cmd`、`MRRC-Modern-Cleanup.cmd`。
这比让客户敲命令好，但客户仍然要：下载文件 → 过一次 UAC → 看一个黑底白字窗口。
对一个业余无线电用户来说，**这三步都是多余的**。

**目标**：把这三件事搬进应用界面——每个都是"点一下"。

| # | 做什么 | 现状 | 还差什么 |
| --- | --- | --- | --- |
| ① | **接入云端** | 设置对话框已有申请/口令/刷新 ✓；**v1.25.0 起批准后无需任何点击** —— 服务端每 30 s 自查一次（`server.py` 的 `_cloud_autoconnect_loop`），发现已批准就自动落证书、登记入口、提示重启 ✓（手动「刷新状态」保留为立即触发） | **已交付**（代码 + `tests/test_cloud_endpoints.py` 里 5 个专项用例：轮询到授予即接入 / 已接入不再轮询 / 与手动登记互斥 / 无申请不起轮询 / 状态端点报告轮询器）。**真机上的自动路径还没跑过**：现场机 `192.168.1.53`（bg6lh）那次登记是人工触发的，"装完不点任何东西、只等批准"这条等着在真机上走一遍 |
| ② | **升级整包** | 有 `upgrade_core` + `latest.json` + 只读端点 `GET /api/update/check` ✓（**界面尚未接**：全仓没有任何界面代码调用它，`static/` 里也没有升级按钮 —— 原写"有一键升级按钮 ✓"经 2026-10-03 实测为假） | 端到端复跑一遍，特别是**静默安装后自己拉起应用**（今天实测：静默安装不会启动应用 ⇒ 装完必须由客户端或安装器拉起 ✓） |
| ③ | **打静态补丁** | 补丁通道已有（`patches/patch.json` + 施加脚本 ✓） | 应用内读取清单 → 按 `version.txt` 匹配 `appliesTo` → 下载 → 校验 SHA-256 → 覆盖 `_internal/static` → 自重启 |

**验收标准**

1. **干净机器**：装包 → 界面点「接入」→ 填呼号 → 等批准 → **自动完成** → 入口 `https://<呼号>.mrrc.vlsc.net/` 返回 401。
   全程不下载任何 `.cmd`、不开命令行。
2. **有补丁时**：界面提示"有可用补丁" → 点一下 → 应用重启 → 新界面生效（可用 `served js 含新符号` 验证）。
3. **每一次失败都必须在界面上说明原因**——今天那场"黑屏"的代价就是**静默降级**：缺证书退成 HTTP、界面只说"起不来"。
   宁可显示一条丑但准确的错误，也不要静默地换一条路走。

**边界（明确不做 / 做不到）**

- 不做默认开启的**静默自动升级**：升级与补丁都必须由用户知情并点一下。
- 热修**只覆盖 `_internal/static/**`**（网页界面与资源）；Python 逻辑冻在可执行文件里，**必须整包升级**。
- 补丁**改版本号**：不改。补丁是同一版本上的替换，`version.txt` 不动（清单用 `appliesTo` 表达适用性）。

**相关**

- 静态补丁的边界与实测记录：`packaging/patch/`、站上 `downloads/patches/patch.json`。
- 施加脚本（可作为应用内逻辑的参考实现）：`tools/windows/MRRC-Modern-Patch.ps1`。
- 接入脚本：`tools/windows/MRRC-Modern-Connect.ps1`。
- 今天的黑屏四个成因（构建机默认值）与三条结构性修法，见 v1.24.5 的 CHANGELOG 条目。

## 2. 盒子源码包做成**可复现**的（同一个提交，每次构建同一串字节）

**背景**（2026-10-22，发 FP1 时撞出来）。`make_box_source.py` 用 `tarfile.open(..., "w:gz")`
打包，gzip 头里写着**构建时刻**，文件条目的 mtime 也来自工作区 —— 同一棵树连打两次：

```
18,647,255 B   f72c9718…      （提交前那次）
18,647,266 B   fe8c07e5…      （提交后那次）
```

内容一字未变，字节却不同。后果不是"哈希难看"，而是**清单里的 SHA 只对"那一次构建"成立**：
谁想复核就得相信那台机器那一刻的时钟；我们甚至不能自己重打一遍再比对。所以实际流程退化成了
"先构建、再手改清单、再提交"，与 AD-022 那句"清单的大小与 SHA 来自产物本身"只差一层运气。

**目标**：`make_box_source.py` 同输入同输出 —— `mtime=0`、固定 `uid/gid/uname/gname`、
条目按名字排序、`gzip.GzipFile(mtime=0)`（或 `gzip -n`）。验收：**连打两次逐字节相同**，
且发布前 `dist/` 里那份与从站上下载回来的逐字节相同（这条今天已经能做，只是靠"别再动工作区"）。

**副产品**：可以加一条守卫 —— "清单的 sha 等于现场重建的 sha"，把现在靠纪律的那一步变成断言。

## 3. 更新包装不回 `fleet/frpc`：盒子自愈链上的一处缺口

**背景**（2026-10-22）。`stage-tree.sh` 按设计排除 `/fleet/`，所以盒子源码包里没有 `frpc`
（它是镜像构建期由 `packaging/common/fetch-frpc.sh` 装进 `$MRRC_HOME/fleet/` 的）。
而 `_cloud_start_tunnel()` 的静默跳过条件之一，恰恰就是 `fleet/frpc` 不存在 —— 于是形成一个
自洽的死循环：**隧道起不来的原因之一是缺 frpc，而"升级"这条唯一的远程修复通道装不回 frpc。**

FP1 之后至少看得见了（设置页会写出缺的路径），但看得见不等于修得好。

**两个候选取舍**（先做哪个要人定）：

1. **把 frpc 放进更新包**：解包时按 aarch64 校验后落到 `fleet/`。代价是 LICENSE/校验/架构判断
   一起进盒子更新链，且 Frp 版本要与 hub 钉死（0.71.0）。
2. **只让它可见并给出可执行下一步**：`/api/update/check` 与设置页在 `fleet/frpc` 缺失时直接写
   "重刷镜像或让运维补这个文件"，不假装升级能修。

**验收**：造一台 `fleet/frpc` 被删掉的盒子 —— ①方案下点一次升级能恢复公网入口；②方案下页面
给出唯一正确的下一步，且不出现"已是最新"这种误导。

**相关**：`tests/test_box_update.py::FixPackTests`（包内 `fixpack.txt` 的落地）、
`packaging/box/README.md` 排障表、`docs/superpowers/specs/2026-10-22-box-fixpack-design.md`。
