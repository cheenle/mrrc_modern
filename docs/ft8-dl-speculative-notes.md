# FT8 弱信号解码：一次思辨研究

> 2026-10-15。这不是实验报告，是一次**从第一性原理重算靶子**的推演，外加两个为验证推演
> 而做的测量。结论会推翻本项目前两轮研究（P3 掩蔽增强、P4 端到端解码器）的前提，
> 所以先把算术摆出来，再摆实测，最后说下一步该做什么、以及哪些还没被证明。

---

## 0. 一句话

**在白噪声里，经典 FT8 解码器已经站在它自己码率的有限块长香农门限上（相差约 0.5 dB），
余量是零。** 因此"提升弱信号解码率"在白噪声里**没有算法空间**——P4 的 0/30 不是实现问题，
是算术问题。唯一能把工作点往下推的经典杠杆是 **AP（先验）解码**，而它的正确框架是
**假设集缩减 / M 元检测**，不是码率降低（后者算出来反而更差，见 §2.1–2.2，那是我第一版
算错、后来更正的地方）。a8 的假设清单从源码数出来是**恰好 128 条 = 2⁷**，联合界的松弛量
给出**约 11 dB 的收益上界**。这条链路在本仓**从协议到原生库全线接通、`ap` 默认还是
`True`，却因为呼号与网格是空串而永不武装**。修正探针的三个 bug（dt 撒出了 a8 的搜索窗、
容差手写成验证值的 6 倍、命中判据用邻域而非文本）之后，两轮配对实测（100 对与 120 对，
换了随机序列）：**AP 多解出 13 条与 20 条、文本逐字正确、220 次配对里没有一次丢失
经典路径已解出的报文**；加上专门的过期先验臂，**316 次试验零发明**。
最深处收益最大（−28 dB：1/30 → 12/30）。但量级远小于 11 dB 上界，原因在 §6(d)：
上界是"在 128 条假设上做**最优**检测"，而 a8 只在一个频率、一次 `la8` 未被清除的
机会里跑一遍清单。增益的机制归因是 **a8 占 11、iaptype 3 占 8、ap0 占 1**（§4.4）——
本文第一版说的"a8 只占 3/13"是拿两个不同总体相减得出的，已作废。

代码侧已落地 **P5a**（§7.0）：运行时把 sequencer 已知的 `my_call`/`dx_call`/`dx_grid`
和忠实映射到 WSJT-X Tx 行的 `qso_progress` 喂进每条解码请求（本地与云端两条路径），
**默认关闭**，`MRRC_FT8_AP_A_PRIORI=1` 打开；关闭时请求帧逐字节不变。
`rx_frequency` 故意不填——那是 P5c。

## 1. 算术：靶子到底在哪

### 1.1 FT8 的码率

一条 FT8 报文 = 174 个码比特，其中 77 是信息（含 14 位 CRC 开销），83 是校验：

```
R = 77 / 174 = 0.4425  信息比特 / 码比特
每符号 3 比特（8-FSK），符号 0.16 s ⇒ 匹配滤波带宽 = 音调间隔 = 6.25 Hz
```

CRC 是**开销不是信息**——它买的是低假解率，不占香农意义上的信息率。

### 1.2 两个尺子要对齐

WSJT-X 报告的 SNR 是 **2500 Hz 参考带宽**下的值。匹配滤波的噪声带宽是 6.25 Hz，所以

```
Es/N0 = SNR(2500 Hz) + 10·log10(2500 / 6.25) = SNR + 26.02 dB
Eb/N0 = Es/N0 − 10·log10(3)                   = SNR + 21.25 dB
```

本仓仿真器 `ml_simulate.noise_floor_power()` 的 docstring 自己写着这条换算
（"the same conversion the decoder makes with its −26.5 dB correction"），
所以**标称 SNR 与解码器报告值是同一把尺**——这一点后面很关键。

### 1.3 渐近香农极限

```
Eb/N0_min = (2^R − 1) / R = (2^0.4425 − 1) / 0.4425 = 0.8112 = −0.91 dB
⇒ SNR_min(2500 Hz) = −0.91 + 4.77 − 26.02 = −22.16 dB
```

### 1.4 有限块长门限（n = 174，这才是真实的门）

正态近似 `R = C − √(V/n)·Q⁻¹(ε)`：

| 目标块错率 ε | V = 0.5 nat² | V = 1.0 nat² |
|---|---|---|
| 10% | **−21.12 dB** | **−20.74 dB** |
| 1% | −20.39 dB | −19.78 dB |

n=174 太短，`√(V/n)·Q⁻¹(ε)` 这一项相对 R 并不小——**有限块长门限比渐近极限高 1.0–1.4 dB**。

### 1.5 实测悬崖正好落在这条线上

同一批仿真（真实噪底 × s3 深配置）：

| 标称 SNR | 召回 | 解码器**自己报告的** SNR 范围 |
|---|---|---|
| −26 dB | 25% (2/8) | **−21 … −19** |
| −24 dB | 87.5% (7/8) | **−21 … −7** |
| −22 dB | 100% (8/8) | −21 … −15 |
| −20 dB | 100% (8/8) | −18 … −8 |

两件事同时成立：

1. **报告值的下界是 −21 dB**——四个标称档位、跨越 6 dB，报告值从未低于 −21。
   这正好是 ε≈10% 的有限块长门限（−21.1 … −20.7 dB）。**解码器的悬崖压在理论门上，
   相差约 0.5 dB。**
2. **标称与报告差 3–7 dB，且离散度极大**（−24 dB 档报告值横跨 −21…−7）。
   这是此前已量过的 Jensen 效应（真实噪底非平稳，解码器逐符号取比值偏向安静时刻）。
   ⇒ **召回曲线的横轴不是绝对 SNR。** 这一条是方法论警告，见 §5。

### 1.6 推论：白噪声里余量为零

如果悬崖已在门限上，那么任何**不改变有效信息率、也不改变信道**的算法改进，
在白噪声里的收益上界就是有限块长与渐近极限之间那 1 dB 量级——而且经典链路已经用
BP + OSD + 9 趟 SIC 把这一段吃掉了。

**P4（端到端/学习型解码器）的 0/30 因此不必归因于实现。** 一个学习解码器最好的结局是
*追平* BP+OSD，而 BP+OSD 已经在门上。这解释了一个此前无法解释的现象：比特准确率
93.7% 却整码字 0/30——不是模型不够好，是**这个工作点上根本不存在"更好"**。

**P3（掩蔽增强）的 +0.5–0.9% 同样自洽**：掩蔽改变的是噪声的时频形状，不是白噪声下的
理论门限；它赚到的那一点，来自真实噪底**非白**的那部分结构。

## 2. 唯一能把门限往下推的经典杠杆：AP —— 但框架必须是检测，不是速率

> **本节第一版算错了，这里是更正后的版本。** 错法很有代表性，所以留着讲清楚。

### 2.1 错误的框架（我第一版写的）

把"已知两个呼号 + 网格 + 进程"当成**码率降低**：真正未知的只剩报告值 ~6 bit，
于是 `R_eff ≈ 6/174 = 0.034`，代进有限块长公式得到门限 ≈ −31 dB，"约 10 dB 收益"。

**代回去验算就崩了。** 每信道使用的能量是 `R·Eb`，不是 `Eb`；漏掉这个 R，
结论正好做反：

```
penalty = √(V/n)·Q⁻¹(ε) = 0.143 bit/use      （n=174 固定，不随 R 缩小）
需要 C  = R + penalty = 0.0402 + 0.143 = 0.183
1 + R·Eb/N0 = 2^0.183  ⇒  Eb/N0 = 0.135 / 0.0402 = +5.26 dB
⇒ SNR(2500 Hz) = 5.26 + 4.77 − 26.02 = −16.05 dB
```

**−16.05 dB 比无先验的 −20.74 dB 还差 4.7 dB。**

### 2.2 这个错法本身是个有用的结论

它说的是：**假如真的把 FT8 重新设计成 R = 0.04 的低码率模式，在 n = 174 这个块长下
反而更差**——因为块长惩罚 0.143 bit/use 是"每信道使用"的固定开销，
速率越低，它占的比例越大。短块长吃不下极低码率的红利。
所以"改协议、加冗余"这条路在这个块长上是不通的（真要改，得连块长一起改）。

### 2.3 正确的框架：AP 是假设集缩减，是 M 元检测

发射机并不知道接收端的先验——它照样发一条 R = 0.4425 的码字。AP 改变的不是码率，
而是**译码器要在多少个假设里挑**：从整码的 2⁹¹ 个码字，缩到 `getmsg()` 生成的那一份清单。

清单是从源码数出来的，不是估的（`vendor/ft8/ft8_a7.f90:377`）：

| i | 生成的报文 |
|---|---|
| 1 | `mycall hiscall` |
| 2, 3, 4 | `… RRR` / `… RR73` / `… 73` |
| 5 | `CQ hiscall hisgrid` |
| 6 | `mycall hiscall hisgrid` |
| 7…206 | 报告阶梯 `isnr = −50 + (i−7)/2`，奇数 i 为 `-12`、偶数为 `R-09` |
| 过滤 | `if(abs(isnr).gt.30) msg=''` |

存活 **恰好 128 条 = 2⁷**（i=1..6 加 i=47..168），`log2(128) = 7.000 bit`。
`tests/ft8/test_ap_probe.py` 里有一份 Python 镜像，断言探针合成的报文在这 128 条里。

联合界的松弛量（目标块错率 0.1，均摊给竞争者）：

| | 竞争假设数 | 每对错误概率上限 | 需要 Q 的自变量 x | x²/2 |
|---|---|---|---|---|
| 整码搜索 | 2⁹¹ | 4.0e-29 | 11.14 | 62.0 |
| **a8 的清单** | **128** | 7.9e-04 | **3.16** | **5.0** |

若两者的码字距离相同（**成立**：128 条是整码的子集，子集的最小距离 ≥ 全码的 d_min），
所需 Eb/N0 之比为 `(3.16/11.14)² = 0.0805`，即 **−10.9 dB**。

⇒ **检测论口径下的收益上界约 11 dB**，与 §2.1 那个错误算法凑出的"10 dB"数值接近，
但来路完全不同，而且这次是上界而非门限：**联合界很松**，两个译码器实际都远离自己的界，
所以真正实现多少**只能测**——这就是 §4 的 P5。

## 3. 代码现实：一台装好了却没加油的机器

AP 在本仓是**全线接通**的：

| 层 | 状态 |
|---|---|
| 协议 schema（`ft8/core/protocol.py`） | 22 个字段，含 `ap`/`ap_width`/`my_call`/`dx_call`/`dx_grid`/`qso_progress`/`utc_hhmmss`/`rx_frequency` ✓ |
| worker（`ft8/core/worker.py:98`） | 22 个字段全部忠实转发 ✓ |
| binding（`ft8/core/binding.py:503`） | `flags` bit0 = `ap`，其余字段逐个写入原生结构 ✓ |
| 原生（`wsjt_improved.f90` / `vendor/ft8_decode.f90`） | `ft8apset` + `ft8_a7d` + `ft8_a8d` 三条路径都在 ✓ |
| 结果字段 | `ap_type`、`quality` 都在 schema 里 ✓ —— **AP 解码是带标记的** |

而运行时只填了两个字段（`ft8/runtime.py:220`）：

```python
DecodeConfig(profile=profile, threads=auto_thread_count())
```

`DecodeConfig` 的默认值是 **`ap=True`**、`my_call=""`、`dx_call=""`、`dx_grid=""`、
`qso_progress=0`、`rx_frequency=1500`。于是原生的武装条件

```fortran
ltry_a8          = ap_enabled .and. len_trim(hiscall) >= 3 .and. len_trim(hisgrid4) >= 4
lenabledxcsearch = ap_enabled .and. len_trim(hiscall) >= 3
```

**恒为假**。准确的说法不是"AP 关着"，而是"**AP 开着、被饿着**"：`ft8apset('','',0,…)`
拿到空串，iaptype 停在 0，a8 从不武装。

### 3.1 三条 AP 路径分别是什么（读源码得出，非文档转述）

| 路径 | 先验从哪来 | 能干什么 |
|---|---|---|
| `ft8apset(mycall12,hiscall12,ncontest,apsym2,aph10)` | 配置里的呼号 + QSO 进程 | 经典符号掩码 AP（iaptype 1–6），给主解码循环加先验 |
| `ft8_a7d(dd,newdat,call_1,call_2,grid4,…)` → iaptype=7 | **频带本身**：循环遍历*已经解出的*报文 `msg0(i,jseq,0)`，从中切出 call_1/call_2/grid4 | **精修**已解出的报文。**不能发现新信号** |
| `ft8_a8d(dd,mycall12,hiscall12,hisgrid,f1=nfqso,…)` → iaptype=8 | 配置里的 my/his 呼号 + his 网格，**且固定在 nfqso 上** | **列表译码**（源码注释自称 list decoding）：把 128 条候选逐条重生成复波形再相关，带概率 `plog` 与 `qual`（`plog<−147` 时降到 0.16） |

> **更正**：本文第一版断言"只有 a8 能无中生有，a7 只能精修"。补齐仪表后的实测
> （§4.4）给出的归因是：**a8 占 11/20、iaptype 3 占 8/20、ap0 占 1/20**。
> 所以 a8 确实是最大的一份，"只有 a8 能无中生有"这半句基本成立；但它并非唯一——
> 主解码循环里的**符号掩码 AP**（`ft8apsetvar`，这里表现为 iaptype 3）贡献了另外
> 8 条，而"喂先验顺带改善了常规译码本身"（ap0）只有 1 条，是少数而非主流。
> 本节早先"a8 只占 3/13"的说法作废，那是拿全部 fed 解码的计数去减增益子集。

a8 的门槛（`vendor/ft8_decode.f90:251`）：`lft8apon` ∧ `ncontest∉{6,7}` ∧ `nzhsym==50`
∧ `la8` ∧ `len(hiscall12)≥3` ∧ `len(hisgrid)≥4` ∧ `ltry_a8`。其中 `la8` 的含义是
**"这条报文还没被正常解出过"**——所以 a8 只在常规解码失败处才出手，这是它的设计意图，
也决定了它该在悬崖以下才被观测到。

## 4. 探针与配对实测（`tools/ft8/ap_probe.py`）

### 4.1 第一轮为什么什么都没测到：两个探针 bug

第一轮三方对照（真关 / 饿着=今天的生产状态 / 喂满）结论是"喂先验没有可测提升"。
读源码之后发现，**这个零结果是探针自己造成的**：

| # | bug | 后果 | 依据 |
|---|---|---|---|
| 1 | dt 均匀撒在 `[DT_MIN, DT_MAX] = [0, 2.5]` s | **a8 的时延搜索只覆盖 dt ∈ [−0.5, +1.5] s**（`lag ∈ [−200,200]` @200 Hz，`j = i + lag + 100`），约 40% 的试验把信号放在 a8 够不着的地方 | `vendor/ft8/ft8_a8d.f90` |
| 2 | 命中判据手写成 25 Hz / 1.5 s | 模块里验证过的容差是 **15 Hz / 0.25 s**，dt 松了 6 倍 ⇒ 真实噪底里**别的电台**被记成"我们的信号"。第一轮因此报出 −30 dB 处 4/20 这种不可能的数字 | `ml_simulate.FREQUENCY_TOLERANCE / DT_TOLERANCE` |

两个 bug 都已修，并且各留了一条测试：`A8HypothesisSpaceTests` 用 Python 镜像
`getmsg()`，断言探针合成的报文**确实在那 128 条假设里**、且 dt 落在 a8 的窗口内；
`ProbeMatchingTests` 用假 batch 断言"邻近的报告值 `-14` 不算命中"、"窗外别的电台不算命中"，
并直接禁止源码里再出现 `<= 25.0` 这类手写容差。

**教训**：合成信号的真值是已知的，命中判据就该是**文本逐字相等**，不是邻域匹配。
邻域匹配只在"不知道真值"的真实语料上才是不得已的选择。

### 4.2 修正后的配对实测

同一份 PCM 先按 AP-off 解一次、再按 AP-fed 解一次（16 个真实噪底 × 25 次 × 4 档 SNR
= 100 对）。报文 `BA4EG JA1VAT -12`（= `getmsg` 的 i=83），dt ≤ 1.4 s，
`rx_frequency` 设为信号实际频率（因为 `nfqso = config%rx_frequency`，见 §6）。

| 标称 SNR | 两臂都解出 | **只有 AP-off 解出（丢失）** | **只有 AP-fed 解出（赚到）** | 都没解出 | `ap_type=8` | 位置上文本不符 |
|---|---|---|---|---|---|---|
| −30 dB | 3 | **0** | 0 | 22 | 0 | 0 |
| −28 dB | 1 | **0** | **5** | 19 | **3** | 1 |
| −26 dB | 9 | **0** | **4** | 12 | 0 | 1 |
| −24 dB | 19 | **0** | **4** | 2 | 0 | 0 |
| **合计** | 32 | **0 / 100** | **13 / 100** | 55 | 3 | 2 |

四条读数：

1. **AP 是并集安全的**：100 次配对里 `only_off` 全为 0——喂先验从未让任何一条已解出的
   报文消失。这与本项目"只增不减"的一贯约束一致，意味着上线不需要回退机制。
2. **收益是真的，且集中在最深处**：−28 dB 处 1/25 → 6/25（相对提升 6 倍）；
   −30 dB 处两臂都是 0（太深，AP 也够不着）。按"AP-off 漏掉的机会"算，13/68 ≈ 19%。
3. **零发明**：两条"位置上文本不符"都是**噪底里别的电台**（`VK4YDF JI1BBN R-12`、
   `CQ BA4IAW OM87`，后者 off 臂也解到了），不是 AP 编出来的。加上第一轮矛盾先验臂的
   0/36，**两次实验都没有观测到 AP 发明报文**。
4. ~~**干活的主要不是 a8**~~ —— **这条推断是错的，见 §4.4 更正。** 它把"全部 fed
   解码里 `ap_type=8` 的条数"当成了"增益里 `ap_type=8` 的条数"，拿两个不同总体相减。
   我在探针注释里写过"靠减法推断机制不是证据"，然后自己正好犯了这个错。

### 4.3 精度臂：先验过期时会发生什么（§7.1 判据 2）

前两轮的世界都是自洽的：第一轮先验正确，第二轮"矛盾"是把别人的 CQ 放在**AP 被告知
要听的那个频率上**。真实场景里的失效更安静——**先验描述的是一场已经不在进行的 QSO**
（对方改了频率、QSO 已结束、网格来自很多槽之前的解码）。

于是第三轮把真信号放在 AP **没有**被指向的频率（偏离 800 Hz，远在 a8 的 ±10 Hz 激活窗
之外），同时照常喂 `my_call`/`dx_call`/`dx_grid`。判据是"发明"：一条同时点名
MY_CALL 与 DX_CALL、却不是我们合成的那条报文的解码——因为发明出来的报文会进 sequencer，
而 sequencer 会按它去按键发射。

| 空中实际的报文 | −20 dB | −24 dB | −28 dB | 发明 |
|---|---|---|---|---|
| `CQ VK3ABC QF22`（无关电台的 CQ） | 真值 20/20 | 16/20 | 10/20 | **0** |
| `JA1VAT BA4EG R-09`（同一对象，但比先验声称的阶段更晚） | 真值 20/20 | 19/20 | 6/20 | **0** |
| `BA4EG JA1VAT QN06`（对方的网格报文，不是我们等的那条报告） | 真值 20/20 | 18/20 | 4/20 | **0** |
| **合计（每格 20 次，共 180 次）** | | | 真值 **133/180** | **发明 0** |

三条读数：

1. **零发明**（180 次）。加上第一轮的 0/36 与第二轮的 0/100，**三次实验、316 次试验，
   没有观测到一次 AP 发明报文**。
2. **真值召回没有受损**：−20 dB 三格全 20/20，−24 dB 16–19/20。错误的先验既没有制造
   假解，也没有挤掉真解。
3. **`ap_type=8` 全程为 0**：a8 在没有匹配假设时根本不开火。它不是"总是给出一个答案"
   的猜测器，`PLOG_MIN = −160` 与 `plog < −147 → qual = 0.16` 那套阈值确实在起作用。

⇒ §7.1 的判据 2（"假解率必须先量再上线"）在合成场景下已满足。仍未覆盖的是
**真实语料上的先验过期**（本轮的噪底是真的，信号是合成的）。

### 4.4 机制归因：补齐仪表之后（P5b）

上一轮留下的缺口是"只记录了 `ap_type == 8` 的次数"（§4.6 第 1 条）。补上完整分布后重跑
（`--paired`，16 噪底 × 30 次 × 4 档 SNR = 120 对），结论与 §4.2 的推断相反：

| 标称 SNR | both | **only_off（丢失）** | **only_fed（赚到）** | neither | wrong_text | **增益的 ap_type 分布** |
|---|---|---|---|---|---|---|
| −30 dB | 3 | 0 | 0 | 27 | 0 | — |
| −28 dB | 1 | **0** | **11** | 18 | 0 | **ap8:8, ap3:3** |
| −26 dB | 15 | **0** | **7** | 8 | 0 | **ap3:4, ap8:3** |
| −24 dB | 25 | **0** | **2** | 3 | 0 | ap0:1, ap3:1 |
| **合计** | 44 | **0 / 120** | **20 / 120** | 56 | **0** | **ap8:11, ap3:8, ap0:1** |

- **a8（列表译码）是最大贡献者：11/20**，不是 3/13。§4.2 的"主要不是 a8"作废。
- **iaptype 3 贡献 8/20**：那是 `naptypes` 表每行开头都有的 `3,3,3`（前三个附加
  译码趟），与 `qso_progress` 无关——这解释了 §4.5 的扫描结果。
- **ap0 只有 1/20**：即"喂先验改善了常规译码本身"这种情况很少。绝大多数增益来自
  两条**带标记**的 AP 路径，这对上线是好消息（可以用 `ap_type != 0` 把它们挑出来）。
- `only_off` 仍是 **0/120**，`wrong_text` 仍是 **0** ⇒ 并集安全与零发明在更大样本上复现。
- −28 dB 处召回 1/30 → 12/30（4% → 40%）。

**`quality` 能不能当闸门（§7.1 判据 3）**——能，而且它把两条机制分得很开：

| 机制 | n | quality 范围 |
|---|---|---|
| `ap8`（a8 列表译码） | 11 | **全部 1.0**（a8 只在 `plog < −147` 时降到 0.16） |
| `ap3`（符号掩码 AP） | 8 | **0.07 – 0.83**（含 0.07、0.085、0.10、0.168 四个低值） |
| `ap0`（常规） | 1 | 0.65 |

这 20 条**文本全部逐字正确**，包括 quality 0.07 那条。但 ap3 只有 8 个样本，
**不足以据此认为低 quality 是安全的**——只能说本轮没观测到低 quality 出错。
上线时仍应按 §7.1 判据 3 使用 `quality`，并对低值条目单独打点观察。

### 4.5 `qso_progress` 扫描：为什么它没有影响

`ft8bvar.f90` 用四张表按 `(nQSOProgress, extra decoding pass)` 选先验掩码
（`naptypes` / `nmycnsaptypes` / `ndxnsaptypes` / `nhaptypes`），行注释直接写着 Tx 阶段：
0 = Tx6 CQ、1 = Tx1 Grid、2 = Tx2 Report、3 = Tx3 RRreport、4 = Tx4 RRR/RR73、5 = Tx5 73。
而 **row 3 / row 4 是唯一带 iaptype 6/5/4（RR73 / 73 / RRR）的行**。

原来的 `_qso_progress()` 只返回 0 或 2，等于把 QSO 后半段全部压到 row 2 —— 译码器
永远不会去试 QSO 收尾阶段最可能出现的那几种报文。已改成按 `QSOState` 忠实映射到
0–5（`QSOState` 自己的 docstring 就写着"maps to WSJT-X Tx1–Tx5"），并加了五条测试，
其中一条专门盯住爆炸半径：`cascade.py:58` 的升级判据是 `qso_progress > 0`，
所以 IDLE / CALLING / DONE 必须仍映射到 0。

但**实测上这个修正没有带来差别**：progress = 0 / 2 / 4 三档在同一批试验上结果
逐格相同（−28 dB：both 0、赚到 2、neither 13；−26 dB：both 8、赚到 2、neither 5）。
原因在表里看得很清楚——**每一行的前三格都是 `3,3,3`**，行与行的差别只出现在
第 4 格以后（`isubp2-4`，即更靠后的附加译码趟），而本轮的增益恰好来自前三趟的
iaptype 3 加上 a8。所以这条修正是"把已经知道的状态如实交出去"，不是收益来源；
真要吃到 row 3/4 的 RR73/73 假设，得让译码走到更靠后的附加趟。

> 一个测量陷阱值得记下：`--snr` 给几档会改变共享随机数发生器的推进量，
> 因此"progress 扫描（−28,−26 两档）"与"P5b（−30…−24 四档）"**抽到的不是同一批
> 试验**，两轮的绝对数字不可直接比较。扫描内部三档之间是同批试验（配对有效），
> 这才是它能得出"无差别"结论的原因。

### 4.6 还没测到的东西

探针只记录了 `ap_type == 8` 的次数，没记录增益条目的完整 `ap_type` 分布，
所以"其余 10 条走的是 iaptype 1–6 还是 ap_type=0 的常规路径"目前只能由
"不是 8"反推。这是下一步要补的第一个仪表（§7）。

## 5. 方法论教训：先换算横轴，再谈优化

本项目前两轮把力气花在 ML 上，依据是"−26 dB 处 69% 的信号被漏掉"。但那条曲线的横轴是
**真实噪底上的标称 SNR**，而 §1.5 量到它与解码器自己的尺子差 **3–7 dB**、离散度极大。

⇒ "−26 dB" 这个说法在绝对意义上不成立。**任何以 SNR 为横轴的结论，都必须先声明用的是
哪把尺**：标称（仿真器的增益律）、解码器报告值（Jensen 抬高的）、还是理论门限所在的
Es/N0。三者在真实噪底上可以差 7 dB，而 7 dB 足以把"还有很大空间"变成"已经在门上"。

这条教训的一般形式：**在优化之前，先把测量轴换算到理论轴上。** 否则会把一个已被
信息论关闭的方向，误读成一个工程问题。

### 6.1 于是"落差"这个问题要重新表述

原来的问法是"为什么实测拿不到 11 dB"。补齐仪表（§4.4）之后，正确的问法是两个：

1. **iaptype 3 那条路径的收益上界是多少？** 它贡献了 8/20，身份已经查清：是
   `naptypes` 每张表**每行开头都有的 `3,3,3`**（前三个附加译码趟），与 `qso_progress`
   无关（§4.5）。它不缩减假设集，而是在 LDPC 迭代里注入先验符号掩码——收益应当用
   "迭代收敛域扩大"来估，而不是用联合界。**这个数我们还没算过。**
2. **a8 已经是最大贡献者（11/20），能不能再多要一点？** 它受三处限制，都可查：
   只在 `rx_frequency` ±10 Hz 内激活（而 P5a 故意没填这个字段，§7.0 约束 3）、
   `la8` 门（±3 Hz 内有任何解码即取消）、`la8owner`（多线程下只有拥有该频段的线程
   跑 a8，`compute_band` 切分 200–3000 Hz）。`plog`/`qual` 阈值这轮看不是瓶颈：
   11 条 a8 增益的 `quality` **全是 1.0**，即没有一条落到 `plog < −147` 那档（§4.4）。

第 2 条是有具体仪表可查的，第 1 条需要新的分析。**两者都不需要机器学习。**

### 7.0 P5a + P5c 已实现：怎么开、开了会发生什么

代码已落地（`ft8/runtime.py`、`ft8/engine/dsp_decode.py`、`ft8/platform/cloud_decode.py`），
**默认关闭**，由一个环境变量打开：

```bash
MRRC_FT8_AP_A_PRIORI=1     # 空 / 0 / false / 未设置 = 关（出厂默认）
```

打开之后，每个时隙的解码请求会带上 sequencer 当时已知的四样东西：

| 字段 | 来源 | 何时有值 |
|---|---|---|
| `my_call` | `sequencer.my_call` | 始终（本站呼号，不会过期） |
| `dx_call` | `sequencer.dx_call` | 有通联对象时 |
| `dx_grid` | `sequencer.dx_grid` | 对方报过网格时 |
| `qso_progress` | `_qso_progress(sequencer.state)` | 始终；按 `QSOState` 映射到 WSJT-X 的 0–5 行（§4.5） |
| `rx_frequency` | **`DxFrequency`**：最近一次听到 `dx_call` 的那条解码的 `result.frequency` | 仅当该次目击**新鲜**（≤6 槽）且仍属于**当前**对象时 |

三条实现约束（都有测试盯着，见 `tests/ft8/engine/test_ap_a_priori.py`）：

1. **关闭时帧逐字节不变**——`ap_context=None` 不许碰任何东西。每一台出厂盒子、
   每一台没配云端的机器，行为与改动前完全一致。
2. **provider 每槽重新读，不缓存**——`dx_call` 会在 QSO 中途变；启动时解析一次的
   值一定会过期，而"过期的先验"正是 §4.3 量的那一档。
3. **`rx_frequency` 只在新鲜时才填**（P5c）。a8 只在其 ±10 Hz 内激活，填错比
   不武装更糟，所以它来自"最近一次听到对方的那条解码"，并且带两道闸：**但这条省略是有代价的，而且代价比本文第一版以为的大**：补齐仪表后
   （§4.4）a8 是最大的一份（11/20），所以**现在这版 P5a 只吃到了 iaptype 3 那 8/20**，
   把最大的机制留在了门外。解锁它是 P5c。

   **P5c 的第一个候选答案是错的，记下来免得再走一遍。** `sequencer.tx_frequency`
   的注释写着「对方被解码时的音频偏移」，看着就是 nfqso；但读它的三个写入点：
   `start_cq()` 把它设成**我们自己**的 CQ 偏移（`cq_loop.py:65` 的 `pick_frequency()`）、
   `reply_to()` 从 `state.selected_freq` 取（操作员在界面上选中那一行时对方的频率，
   UC-003 的注释确认了这个语义）、`_reset_partner()` 复位成 1500。而
   `on_message(msg, snr_db)` **不带频率参数**，所以 QSO 推进过程中它不会跟着对方的
   新解码更新。⇒ 它是「我方发射偏移」，只在「操作员刚点完回复」那一刻恰好等于对方频率；
   进入 REPORT / ROGERS / SIGNOFF 之后就是**选中当时的冻结值**。对方在 HF 上漂走，
   a8 就会被指向一个空频率。

   正确的来源在编排层就有：`orchestrator.py:382` 那个循环手里的 `message.result`
   是带 `frequency` 的，只是没往下传。P5c 的最小改法是在运行时的解码回调里记
   「最近一次来自 `dx_call` 的频率 + 槽号」，只在若干槽内新鲜时才填 `rx_frequency`
   ——**过期的频率比不填更糟**，因为 a8 会真的跑到那个频率上去试 128 条假设。

   安全性这一档已经量过：§4.3 的过期先验臂正是「真信号偏 800 Hz、a8 指向空频率」，
   180 次试验零发明、`ap_type=8` 全程不开火。

   **P5c 的实现**（`ft8/runtime.py`）：`DxFrequency` 记住 `(call, frequency, slot_id)`，
   由 `_on_batch → _note_partner_frequency` 每槽喂入，`fresh_for(call, slot_id)` 回答
   "这个频率现在还能不能用"。两道闸：

   * **新鲜度**：`age = (slot − 记录槽) mod 5760 ≤ 6`。对方隔槽发射，6 槽 ≈ 90 s
     容得下一次漏解加余量。窗口故意放宽，因为两侧的代价不对称——指向空频率的实测
     代价是零发明（§4.3），而窗口太紧只是白白放弃最大的那份收益（a8 = 11/20）。
     取模是为了跨午夜不会突然变成"很旧"。
   * **归属**：记录里的呼号必须等于**当前** `dx_call`。操作员换了对象之后，
     拿上一个对象的频率去武装 a8 比不武装更糟。

   另外三条边界，都有测试盯着：迟到批次不喂（NFR-001/NFR-009 规定它只用于显示，
   编排层同样不把它喂给 sequencer）；**预备批次要喂**（对方的报文常常先出现在快答案里，
   而"更新"正是这件事的全部意义）；`tx_frequency` 仍然不填——`nftx` 的语义是**我方**
   发射偏移，而探针当时填的是信号频率，照搬过来是另一个没量过的配置。

   最后一条测试是"发货的等于量过的"：`test_the_shipped_config_matches_the_measured_one`
   把运行时真正构造出的 `DecodeConfig` 与探针 `ap_fed` 臂的配置逐字段对比，
   断言差异**只**允许出现在 `tx_frequency`（故意）与 `utc_hhmmss`（逐槽）。
   §4.2/§4.4 那些数字是用探针的配置量出来的；运行时一旦漂移，证据就不再适用于
   发货代码——所以这条差异是被点名钉住的，不是默认放过的。

云端路径同样带上这份先验（`cloud_decoder_from_environ(..., ap_context=...)`）：
主机跑的是同一个原生解码器，而配置本来就随每个请求整份发过去，**不增加任何线上开销**。

### 7.1 P5a 的上线判据（写下来，免得事后找理由）

1. **只增不减**：AP 解出的报文与常规解出的一起进并集；`ap_type != 0` 的条目在 UI 上
   带标记（结果 schema 里已有 `ap_type` 与 `quality` 两个字段，§3 表格）。
2. **假解率必须先量再上线 —— 已测**：§4.3 专门量了"先验过期"这一档（真信号放在
   AP 没被指向的频率上，先验照常喂），180 次试验**零发明**、真值召回未受损、
   `ap_type=8` 全程不开火。三次实验合计 316 次试验零发明。仍未覆盖的是真实语料上
   的先验过期（噪底是真的，信号是合成的）。
3. **`qual` 要参与决策**：`plog < −147` 时 a8 自己把 `qual` 降到 0.16——这是解码器
   在说"这条我不太确定"。运行时应当用它，而不是把 AP 解出的一律当真。

   **前提是先看得见**：计数器只写不读等于没写，所以 `OrchestratorCounters` 新增了
   `ap_decodes`（本槽最终批次里 `ap_type != 0` 的报文数）与 `ap_low_quality`
   （其中 `quality < AP_LOW_QUALITY = 0.5` 的条数）。两个数都进了状态栏快照与
   `engine` payload。0.5 这条界取自解码器自己的语义而不是拍脑袋：它落在
   "a8 的高置信 1.0"与"a8 自己认为可疑的 0.16"之间（§4.4 实测 iaptype 3 那一路
   散布在 0.07–0.83），所以 `ap_low_quality` 数的是**解码器自己都没把握的那部分**。

   这两个数是打开开关之后**唯一**能回答"AP 今天解出了几条、其中几条它自己心虚"的
   读数——§4.4 的 20/120 是合成信号上量的，线上只有它们。

## 8. 本文没有证明的东西

- **没有证明 AP 在真实 QSO 中能提升召回。** §4.2 的 13/100、§4.4 的 20/120 与 §4.3 的
  零发明都是"合成信号 + 真实噪底"的结果：信号是我们放进去的，位置、强度、内容全已知。
  真实 QSO 里先验过期的形态更复杂（对方改频、QSO 已结束、网格来自很多槽之前的解码、
  多站同时呼叫），而那一档**只有合成近似**（§4.3 用 800 Hz 频偏模拟"对方不在我以为的
  频率"）。
- **P5a + P5c 已经写进代码，但一次都没有在真实 QSO 上跑过。** 它默认关闭
  （`MRRC_FT8_AP_A_PRIORI` 未设置），所以线上行为与改动前逐字节相同；打开之后会怎样，
  目前只有合成证据。特别地，`DxFrequency` 的 6 槽新鲜窗口是**推理出来的**（对方隔槽
  发射 + 容一次漏解），不是从真实 QSO 的频率漂移统计里量出来的。
- **`test_the_shipped_config_matches_the_measured_one` 保证的是"配置一致"，不是
  "效果一致"**：它钉住运行时构造出的 `DecodeConfig` 与探针 `ap_fed` 臂逐字段相同
  （只差 `tx_frequency` 与 `utc_hhmmss`）。真实电台上的收益仍然要打开开关去量。
- **没有证明 11 dB 可达。** §2.3 是联合界口径的**上界**；实测 20/120 离它很远，
  原因见 §6(d)——a8 只在 `rx_frequency` ±10 Hz 内、`la8` 未被清除时跑一次清单，
  而 11 dB 假设的是在这 128 条上做**最优**检测。
- **§6(a) 的原生状态泄漏没有被判决**，只是被配对设计削弱到不影响结论。
- **没有拆分各先验字段的边际贡献，也没有量化 iaptype 3 那条路径**：本轮只有
  "四个先验一起喂"这一档，所以无法回答"只喂呼号够不够""网格值多少"；而 iaptype 3
  贡献了 8/20 的增益（§4.4），既没有理论也没有单独对照。
- **没有验证 `ap_type` 与原生 `iaptype` 的一一对应**：§4.4 的分布是直接观测到的
  0/3/8 三个取值，但"iaptype 3 就是 `naptypes` 每行开头那个 3"是由表结构推的，
  没有在原生侧打印过。
- 没有在 GPU 上训练过任何模型；本文所有算力数字都是外推。
- 有限块长计算用了正态近似与 V ∈ {0.5, 1.0}；n=174 时正态近似本身误差不可忽略，
  表中数字应读作量级与位置，不是小数点后一位的承诺。
- 香农极限按**相干** 8-FSK 计算。若链路存在未建模的相位噪声/频偏残余，真实门限更差——
  这只会让"白噪声余量为零"更强，不会更弱。
- §2.1 那个"−31 dB"是**错的**，留在文里是为了记录错法；正确读法见 §2.2–2.3。
