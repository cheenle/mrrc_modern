# FTX-1 深度技术分析

**一句话**：FTX-1 不是一台电台。它是几个各自带固件的盒子，被一条 ASCII 总线缝在一起。缝线在哪，协议里看得见。

资料来源三处，文中不逐一标注：

- Yaesu《FTX-1 CAT Operation Reference Manual》，取自 `rzochowski/cat-ftx1` 仓库的 `docs/CAT-FTX1.pdf`（正文 2211 行，含 444 行菜单表）。下文的命令格式、位宽、默认值、菜单项，凡未注明者都出自这里。
- 第三方实现 `cat-ftx1/serial-server.mjs`（770 行，Node，2026-08 仍在维护）。它提供了手册没有的两类东西：真机行为，和作者踩过的坑。
- 本仓 `backends/yaesu/`、`backends/ft710/`、`backends/ic7300/`（我们的实现，作为对照）。

## 摘要

- **fact**　`VE` 命令能读出六个固件版本：MAIN CPU、DISPLAY CPU、SDR、DSP、SPA-1、FC-80。一台电台里有六个可独立升级的处理器。
- **fact**　CAT 走 ASCII + `;`，命令表列了八十余条命令，四列语义：Set / Read / Ans / AI。
- **fact**　`SM`、`MR`、`ID`、`VE` 的 AI 列是 `X`：主动信息模式不推表计，也不推版本。
- **fact**　`SS` 只能设频谱显示（速度、峰值、标记、颜色、电平、span、显示模式、AF-FFT），**没有任何一条命令能读回扫频数据**。
- **fact**　按手册把本仓实际发出的每一条命令逐字核对，FTX-1 路径上共 20 项不符：3 条多写了通道位、3 条位宽错、4 条形状或语义错、6 条命令在这个机型上根本不存在、4 条读错字段或能力表不符。清单见第十二节，逐条对照见附录 C。
- **inference**　FTX-1 的 CAT 面是"FT-710 的 HF 面"乘上"C4FM/APRS 手持机系的面"拼合出来的，两面的接缝就是它最难用的地方（证据见第八、九节里的矛盾表）。
- **thesis**　因此远程控制的实时性只能来自轮询。指望 AI 省掉轮询，是把协议读错了。
- **excluded**　手册里没有 `AN`（天线选择）这类命令，也没有 SD 卡文件读写与双接收音频分路。天线选择藏在 `EX` 里，SD 卡只能被“更新固件/存读信道表”这类动作触发，两路 RX 音频怎么分发不归 CAT 管。这三样找过，没有。

## 一　六个 CPU

`VE` 不是软件版本号，是一张拓扑枚举。P1 的 0..5 依次是 MAIN CPU、DISPLAY CPU、SDR、DSP、SPA-1、FC-80，应答是五位 BCD。

这一条把整机的形状交代清楚了。**SDR 与 DSP 是两个独立的处理器**：前者管射频采样与解调，后者管音频域的滤波、降噪、均衡。**SPA-1 和 FC-80 也有自己的 CPU**：功率放大器与外置天调走的是独立固件，只是被主机枚举进来。

推论很直接：一台"电台"里的故障域有六个。升级只升 MAIN，SDR 那一侧的行为就可能对不上；报告"CAT 不好用"，先要看 MAIN 是不是 1.08 以上——手册开篇第一句就是**MAIN 固件低于 1.08 时 CAT 完全不工作**。这不是兼容性提示，是功能性前提。

工程上还有一层：`VE` 是只读的（Set 列 `X`），而且不进 AI。要判断对面接的是 Field head 还是 Optima，读 `VE4` 看不出来；要看 `PC` 的 P1（第九节）。

## 二　三条串口

USB-C 一进主机，出来两条 UART，芯片是 Silicon Labs 的 CP210x 双 UART（手册里的 Enhanced COM Port 与 Standard COM Port 就是它的两个口）。第三条口不在 USB 上，在后背的 TUNER/LINEAR 插座里：

| 口 | 默认 | 停止位 | 用途 |
|---|---|---|---|
| CAT-1 | 38400 | 可选 1/2 | CAT 通信：频率、模式、菜单 |
| CAT-2 | **4800** | 固定 1 | TX 控制（PTT、CW 键控、数字模式），也可跑 CAT |
| CAT-3 | 38400 | 可选 1/2 | 走 TUNER/LINEAR 插座，5V CMOS |

三条口的默认波特率不对称。CAT-2 出厂 4800 而 CAT-1 出厂 38400，这不是笔误：CAT-2 的原职是"用 RTS/DTR 拉 PTT、发 CW"，数据量小；真当 CAT 用，得自己去菜单里改。

第三条口是一个复用插座，菜单 `TUN/LIN PORT SELECT` 四选一：**EXT-TUNER / LINEAR / CAT-3 / GPO**。

这一格是整机最硬的约束。CAT-3 与外部天调、线性功放、四路 GP 输出**互斥**——你不可能一边用 CAT-3 遥控、一边让外置天调占用这个插座。第三方实现 README 里那句"用 SPA-1 时 CAT-3 归它，别动参数"，说的就是这里：SPA-1 是以总线设备身份挂在 CAT-3 上的。

`GP` 是四路 5V CMOS 输出，最大 3 mA，只能拉逻辑，不能驱动继电器。想控制天线切换器，中间还得加一级。

## 三　四列命令表

命令表不是一张表，是四张叠在一起：

`Set / Read / Ans / AI`。

`AB` 是 `O X X X`：能写，读不出来，不应答，不推送。`SM` 是 `X O O X`：不能写，能读，会应答，**不推送**。`RI` 是 `X O O O`：能读，而且 AI 会主动推。

这四列的分工比命令名本身更重要。它告诉写客户端的人：哪些状态是"事件的"（AI 推），哪些是"轮询的"（AI 不推），哪些是"只写的"（写完就不知道结果，只能靠另一条命令反查）。

位宽是固定的，手册专门用一段纠错示例讲这件事：`IS` 的正确参数是 `IS00+1000`，少一个方向符号、少一位数字、多一位数字、中间插空格，全是错的。**参数长度是协议契约，不是格式建议**。本仓 `backends/yaesu/cat_core.py` 的 `RL`（DNR 等级）发的是 `RL0` 加三位数，FTX-1 手册要求的是 `RL` 加通道位再加两位数——一字之差，命令不生效，回一个 `?`（第三方的错误处理里就这一行代码）。这句话不是举例：照它把本仓发出去的每一条都核一遍，查出 20 项不符（第十二节）。

## 四　AI 只推一半

`AI1` 打开后，电台把状态变化主动吐出来，不必一问一答。这常被理解成"实时性的来源"。看那一列 `X` 就知道不成立：

`SM`（S 表）、`RM`（各表计）、`MR`（存储信道读）、`ID`、`VE` 的 AI 列全是否。

也就是说，**AI 推的是"用户拧旋钮"这一类事件**——频率、模式、增益、AGC、VOX、频谱设置、`RI` 状态字；**它不推表计**。任何一个要画 S 表的界面，都必须自己轮询 `SM` 或 `RM`，AI 帮不上忙。

第三方实现的轮询结构正好印证：连上后先跑两批初始化查询，然后 `SM0`/`SM1` 每 500 ms 一轮，`GT0/AG0/RG0/PC` 每 3 s 一轮。AI1 开着，照轮不误。

顺带一个协议层的坑：AI 帧是**没有请求上下文**的。一问一答时，客户端知道"这条 `SM` 应答是我刚才问 `SM1` 的回音"；AI 主动推的时候，这个上下文不存在。而 FTX-1 的 `SM` 应答里那个通道字节，第三方作者的注释写得很直白——**无论你查主还是副，它总是回 0**。第五节接着讲。

## 五　一个通道位

双接收在这台机器上是真双收，不是一个混频器切两次：`FR00` 是 dual receive，`FR01` 是 single receive；`VS` 选"主 TX/RX + 副 RX"还是倒过来；`FT` 选发射用哪个 VFO；`FA`/`FB` 分别是主副频率；`AB`/`BA` 是两面互拷。

协议里标识通道的只有 P1 这一位（0 主 1 副）。问题在于应答不可信：

- `SM` 的应答通道字节恒为 0（第三方实测注释）。
- 设置副 VFO 的静噪，电台会回报**主** VFO 的变化（第三方 README 原话："correctly sets the value, but the transceiver reports that the value for VFO Main has been changed"）。

两条加起来，得到一个不好听但必须接受的结论：**通道身份只能由请求方持有，不能从应答体里读回来**。客户端必须把"我在问谁"绑在请求上，等回音时用请求的身份解释回音，而不是解析回音里的字节。

本仓的 `YaesuCatController.query()` 是按前缀匹配应答的，请求上下文在手，方向是对的；但 `get_s_meter()` 只读 `SM0`、取 `resp[3:]`，等于**只支持主通道**。副通道的 S 表今天没人问，将来要问，就得先补这层上下文。

## 六　能设不能读

`SS` 是整份手册里最容易误判的一条命令。它有八个子参数：

| P2 | 含义 | 取值 |
|---|---|---|
| 0 | SPEED | SLOW1/2、FAST1/2/3、STOP |
| 1 | PEAK | LV1–LV5 |
| 2 | MARKER | OFF / ON |
| 3 | COLOR | 0–A，**十六进制** |
| 4 | LEVEL | −30.0 … +30.0 dB，0.5 dB 步 |
| 5 | SPAN | 5/10/20/50/100/200/500 kHz、1 MHz |
| 6 | MODE | 3DSS 与 W/F 各自的 CENTER/CURSOR/FIX |
| 7 | AF-FFT / 示波器 | 衰减 0/10/20 dB、时基 1–300 ms、RX/TX 电平档 |

八项全是**显示参数**。整份手册里没有一条命令能把扫频点读出来。

这条事实决定了三件事。第一，FTX-1 的频谱是**在机器里画完给人看的**，不是一条数据流。第二，我们 `backends/yaesu/backend.py` 里 `scope_type="none"` 是对的，但注释"no documented CAT waveform"说得太窄。该说的是"CAT 只提供配置，不提供数据"。第三，这也是 FT-710 那条路必须存在的原因：同为 Yaesu HF SDR，FT-710 的扫频数据走 FT4222 的 SPI，得开一个独立进程去抢设备。

对照一下 Icom：CI-V 的 `0x27` 就是把扫频波形送上总线的命令，我们的 `backends/ic7300/civ_scope.py` 靠它拼出 475 或 689 点。**Yaesu 把扫频留在自己的屏里，Icom 把它放上了总线。** 两家对这个问题的答案不同，不是代差，是取舍。

`SS` 的子参数 7 还透露了另一件事：这块屏不只显示射频谱，还能显示**音频频谱和时域波形**，RX/TX 各有电平档，时基从 1 ms 到 300 ms。频谱显示在这台机器上是 DSP 域的一个功能，不是射频前端的专属产物。

## 七　接收链密度

把菜单表里 HF 那一半的参数排开，会看到一条比多数"便携机"厚得多的接收链：

- LCUT / HCUT：截止频率 100–1000 Hz 与 700–4000 Hz，50 Hz 一步，斜率各两档（6 / 18 dB/oct）。
- `SH` 带宽：P3 索引 00–23，SSB 那一列从 300 Hz 到 4000 Hz，配 `NA` 的窄带开关。菜单里的 NAR WIDTH 表却只列到 22（4000 Hz 落在 23）——差这一格，手册自己也没说清。
- CONTOUR：电平 −40…+20，宽度 01–11，配 APF 宽度三档。
- IF NOTCH 宽窄两档，NB 用 `NL` 走 000–010（000 即关），DNR 用 `RL` 走 00–10（00 即关）。
- AGC 三段（FAST/MID/SLOW）的延迟各自 20–4000 ms，20 ms 一步，另有三个 AUTO 档。
- 发射侧：三段参数均衡（频率/电平/带宽）、TX BPF 五组、AMC 输出 001–100 加 RELEASE TIME 三档。

参数密度接近台机，值域精确到 50 Hz 与 20 ms。归属也看得见：LCUT/HCUT 在 MODE 组的模式页下，NOTCH、NB、APF、CONTOUR 归在 `RX-DSP` 组，而 `VE` 里恰好有一个 DSP 处理器（P1=3）——最合理的解释是这些菜单项改的是 DSP 固件里的系数，不是射频链路。

顺便一条协议习惯：FTX-1 没有 `NB`、`NR` 这两条开关命令，开关被折进了数值命令的 0。**一个值同时表达"关"与"第几档"**，命令数就少一半。我们的 `set_noise_blanker()` 与 `set_noise_reduction()` 发的正是 `NB0x`、`NR0x`——在 FT-710 上成立，在 FTX-1 上不存在。

AMC 值得单独一句。Yaesu 把它和压缩器分成两个命令（`AO` 与 `PR`/`PL`），因为它管的不是峰值，是**说话的平均功率**——压缩器压峰值，AMC 约束平均值。远程发射时这一项比压缩器更影响对方听到的响度一致性。

## 八　菜单是寄存器

`EX` 的地址是五段：`EX` + P1(01–07) + P2(01–07) + P3(01–26) + P4，P4 的位数按项而定，1 到 4 位，最长的文本项 16 位。

444 行菜单表、267 个不同的菜单项名。这是一份寄存器映射，不是设置文件：

- 值是数字的（`AGC FAST DELAY` 0020–4000，4 位；`NAR WIDTH` 00–22，2 位）；
- 值是枚举的（`MOD SOURCE` 0 MIC / 1 USB / 2 Bluetooth / 3 AUTO）；
- 值是**动作**的（`BEACON`、`TX BEACON`、`MEM LIST SAVE`、`MEMORY CLEAR`、`FIRMWARE UPDATE`、`ALL RESET`）——没有参数，写了就执行。

第四类容易被忽略。菜单里混着动作，意味着一个"把 EX 全表读一遍存成配置"的程序是错的：读到动作项会触发它。

对客户端的要求也就出来了：**没有一个通用 setter 能覆盖 EX**。每一项的宽度、值域、是否动作、是否只读，都得查表。这也解释了我们仓库里为什么至今没有 EX 抽象：`backends/ft710/backend.py` 里只有两条硬编码的 `EX040101` / `EX040200`，是开扫频输出的开关，别的一概不碰。要想让 FTX-1 的 AMC、AGC 延迟、LCUT/HCUT、ANT2、APRS 可远程配置，先得把这张表搬进代码，做成"项 → 宽度/值域/类型"的查表。

## 九　P1 即机型

`PC` 的 P1 不是功率值的一部分，是**机型身份**：

- `PC1` + 三位：005–010 W，FTX-1 field head。
- `PC2` + 三位：005–100 W，SPA-1。

手册把这句话直接写在参数说明里。所以"这台机器现在有多大功率"不需要猜，也不需要问用户，读一次 `PC` 就有答案——本仓 `yaesu_profiles.py` 里 `power_format="auto"` 的设计正好对上，只有 `auto` 这一档是诚实的。

菜单表在这一节露出了接缝。同一个 P1=03 组里，"TX GENERAL"的功率项写的是 HF/50M 各 005–010、70M 005–060、144M/430M 005–100；"OPTION"组里写的是 HF/50M 各 005–100、70M/144M/430M 各 005–050，外加 AM 独立限值。两套数字放在同一份手册里，互相矛盾。

合理的解释不是笔误，是**拼合**：一份菜单表服务多个配置（机身 / Optima / 地区变体），共用编号区间，标注没有清干净。这条观察有实用价值——**菜单项存在，不等于本机型可以设**。写客户端时，值域要从读回里学，不能从手册抄。

## 十　一帧两表

`RM` 是这台机器表计系统的核心，它的 P1 不是"读哪个表"，而是两种读法：

- `RM0`：一帧回两个 S 表——主 3 位 + 副 3 位。
- `RM1` S(主)、`RM2` S(副)、`RM3` COMP、`RM4` ALC、`RM5` PO、`RM6` SWR、**`RM7` IDD、`RM8` VDD**。

`RM0` 的设计值得抄：双收的两路电平在一个应答里，帧数减半，轮询预算也减半。（顺手一个反面教材：第三方实现取副表时用了四位，手册写的是三位，多半是偏移算错。一帧多字段的命令，偏移是最容易错的地方。）

后两项修正了本仓的一个假设。`yaesu_profiles.py` 里 FTX-1 的 `has_vd_id_meters=False`，`static/ft710_ui.js` 据此把电压电流那一行藏掉；而手册给了 IDD 与 VDD 两条命令。这是可以直接落地的一处改动（曲线与量程仍需硬件确认，见附录 B）。

`RI` 是另一条被低估的命令。它一次回八位状态：Hi-SWR 标志、录音/回放状态、TX / TX INHIBIT、天调是否正在调谐、扫描状态、静噪开合。

这八位比"从别的现象里猜"可靠得多。远程操作里最怕的是"不知道对面在干什么"：按了 TUNE 却没有天线在动、对方开了 TX INHIBIT 而界面还在等 PTT 成功、静噪没开却以为没信号。`RI` 把这几个都答了。本仓 FT-710 后端读过 `RI0`（`cat_controller.py` 的 `parse_radio_info`），Yaesu 核心（`backends/yaesu/cat_core.py`）里没有——FTX-1 用得着它。

## 十一　三个发射入口

FTX-1 能被点着的地方有三个：

1. CAT 的 `TX` 命令。P1 只有三个值，含义比通常写的细：`0` = 电台不发、CAT 也不要求发；`1` = 电台不发、**CAT 要求发**；`2` = 电台**在发**、但不是 CAT 要的（手册括号里注的是 "Answer"）。
2. 串口硬件线：`RPTT SELECT` 让 RTS 或 DTR 直接拉 PTT，`PC KEYING` 同理用于 CW。
3. 面板与手咪。

那个 `2` 值值得单说。它是电台自己对"这个键不是我按的"的判定：面板、手咪或者外部硬件线把机器顶上了发射，而 CAT 没发过命令。客户端轮询 `TX`，就能在自己的意图与电台的事实之间做一次对齐——自己以为发射中而收到 `2`，那就是别人在按。

这和通常意义的 TX INHIBIT 不是一件事。后者是菜单里的一道锁，由 `RI` 的第四位回报（`2` = TX INHIBIT）。一个是"现在谁在发"，一个是"允许不允许发"。两者都读得到，恰好是一对。

再看第二条。手册专门警告：用 CAT-2 跑 CAT 又开了 RTS/DTR 流控时，必须把 `RPTT SELECT` 设为 OFF，否则电台会在计算机启动时自己进发射。也就是说，**发射入口之间没有互斥**：软件在发 `TX0` 释放，硬件那条线可能还拉着。

因此远程控制的安全设计不能只做在服务端。我们这套系统在服务端做 PTT 仲裁（谁持键谁的释放才算数）、做心跳闸门、做最长发射时长（见 SDD §15）。电台那侧能读到的有两样：`TX` 的 `2`（有人在别处按了键）和 `RI` 的第四位（含 TX INHIBIT）。**服务端认为的发射状态，和电台实际的发射状态，需要有一个交叉校验点**，这两条命令就是那个点。

## 十二　落点

按手册把 `backends/yaesu/cat_core.py` 与 `backend.py` 实际发出的每一条命令核了一遍，FTX-1 路径上共 **20 项不符**。它们不是一类错误，分五类，代价也不同。

### 一类·多了一个通道位

这三条命令在 FTX-1 上**没有**通道位，参数是三位纯数字。本仓统一按 `X0` + 三位发，等于多一个字符。

| 命令 | 手册 | 本仓 | 后果 |
|---|---|---|---|
| `MG`（麦克风增益） | `MG` + 3 位 | `MG0` + 3 位 | 设置不生效 |
| `PL`（语音处理电平） | `PL` + 3 位 | `PL0` + 3 位 | 设置不生效 |
| `AO`（AMC 电平） | `AO` + 3 位 | `AO0` + 3 位 | 设置不生效 |

代码里 `set_mic_gain()` 的注释写着"Family form is `MG P1 P2P2P2` with P1=0"——这条假设在 FTX-1 手册上不成立，该注释本身要改。

### 二类·位宽不符

| 命令 | 手册 | 本仓 | 后果 |
|---|---|---|---|
| `RL`（DNR 等级） | `RL` + 通道 + **2** 位（00 = 关） | 3 位 | 设置不生效 |
| `KP`（键音高） | `KP` + **2** 位（00–75） | 3 位 | 设置不生效 |
| `RA`（衰减器） | P2 只有 `0`/`1` | 把 0–8 的档位索引当 P2 发 | 索引 ≥2 时参数越界 |

### 三类·形状或语义不符

| 命令 | 手册 | 本仓 | 后果 |
|---|---|---|---|
| `PC`（功率设置） | `PC` + P1（**1 = 机身，2 = SPA-1**）+ 3 位 | `PC` + 3 位 | 缺机型位，P1=0 非法 |
| `AC`（天调） | `AC` + P1 + P2 + P3（**P3=3 才是启动调谐**） | `AC0` / `AC1` | 形状错；FTX-1 当前不走它（`tune_via="tx2"`），但其余机型会 |
| `PR`（压缩器） | P2 是 **1 = OFF、2 = ON** | 发 0 / 1 | `PR01` 等于**关**掉它 |
| `ML`（监听） | `ML` + P1 + 3 位；P1=0 时 `001` = 开 | 发 `ML01`（4 字符）与 `ML0` + 3 位两种 | 开关与电平互相混用 |

`PR` 那一条最值得记住：它不是失效，是**反着执行**。用户按下"压缩"，机器把压缩关掉。

还有一处悬而未决，不属于错误但必须标出来：FTX-1 配置的是 `tune_via="tx2"`，调谐靠发 `TX2` 起载波。而手册把 `TX` 的 `2` 注为 **Answer** 形态（电台在发、但不是 CAT 要的）——它作为 Set 命令是否合法，手册没说。真机验证之前，不要在文档或注释里把它当成已确认的调谐路径。

### 四类·命令在 FTX-1 上不存在

| 命令 | 本仓用途 | FTX-1 的对应路径 |
|---|---|---|
| `AN` | 天线选择 | 菜单项 `EX 03-07-04` |
| `NB` | 噪声消除开关 | `NL` 的 `000`（0 = 关） |
| `NR` | 降噪开关 | `RL` 的 `00` |
| `RT` | RX 增量调谐开关 | `CF` 的 P3=0、P4 |
| `RU` | 增量调谐频率 | `CF` 的 P3=1、P5–P8（四位 ±Hz） |
| `XT` | TX 增量调谐开关 | `CF` 的 P3=0、P5 |

FTX-1 把 CLAR 收进了 `CF` 一条命令，用 P3 在两个子功能之间切换：`0` 设开关（P4 RX、P5 TX），`1` 设频率（P5–P8）。本仓那三条 `RT`/`RU`/`XT` 是别的机型的形式。

### 五类·读错字段或能力表不符

| 项 | 现状 | 事实 |
|---|---|---|
| 离开存储模式 | `_leave_memory_mode_if_needed()` 读 `VM` 应答的 `resp[2]` | `resp[2]` 是 P1（主/副），模式在 `resp[3:5]`，存储模式是 `11` |
| `has_vd_id_meters` | False | `RM7` IDD / `RM8` VDD 存在；**但曲线不知道，不能盲改** |
| `att_steps` | 9 档（0–24 dB） | CAT 的 `RA` 只有 ON/OFF；阶梯来自 Hamlib，菜单里有，CAT 不给 |
| `PA` 的 P1 | 固定 `0` | P1 是**频段**（0 HF/50、1 VHF、2 UHF），固定 0 等于 144/430 上的前置放大设置不会生效 |

### 还没做的（不是缺陷）

`RI`（八位状态字）、`IS`（IF shift）、`FR`/`FT`（双收与发射侧）、`EX`（444 行菜单）、`CF`/`EO`、`BS`/`SV`、`IF`/`OI`、`MC`/`MR`/`MW` 那一组存储命令、`GP`、`VE`、`SS`——手册里都在，本仓一条也没发。这是覆盖面问题，不是错误，但 `RI` 与 `TX` 的 `2` 值得优先补（见第十、十一节）。

### 修法

五类不符，三套改法，不要混在一起做：

1. **位宽类（一类、二类）**：改字符串，不碰语义。六处替换，每处一条测试。
2. **形状类（三类）**：`PC` 要接上已有的 `detect_power_config()`（它已经读出了机型位，只是设置时没用）；`AC` 要把"启动调谐"变成 `AC` + P1 + P2 + `3`；`PR` 的 1/2 映射与 `ML` 的 P1 分家要动 `backend.py` 的调用点。
3. **不存在类（四类）**：不能删。`cat_core.py` 是五个机型共用的传输层，删掉会打断 FTDX10、FTDX101、FT-891（它们未必没有这三条）。改法是像 `filter_width_prefix` 那样，把"这个机型有没有这条命令"变成 profile 里的一格能力声明——**共用传输层，各机型自己报能力**。

五类里的 `PA` 与 `RA` 属于同一种改造：把"频段"与"档位"变成 `__set` 的入参，而不是藏在常量 `0` 里。`VM` 的读法只是取错了切片（`resp[2]` → `resp[3:5]`），测试里钉一条断言就完。`att_steps` 与 `has_vd_id_meters` 两处**不要提前改**：前者要把 FTX-1 的 `att_steps` 缩成 `(0, 1)`（ON/OFF），否则 UI 会给出不存在的档位；后者要等真机读数出来再翻。

一条提醒：本轮的核对只对 FTX-1 成立。另外四个机型没有手册在手，以 Hamlib 为准，**未逐条核对**。因此任何修改都必须按机型分开验证，不能"顺手全改"。

### 连带要改的三句 SDD

手册把一件事钉死了：**不是"扫频波形没人公开"，是"协议里没有这条命令"**。SDD 有三处还写着前一种说法，与 SDD/09、SDD/14 自己的描述也不一致，待下次 SDD 升版时改：

| 文件:行 | 现文 | 建议 |
|---|---|---|
| `SDD/01-executive-summary.md:5` | "the Yaesu scope waveform is not documented anywhere" | "the FTX-1 CAT reference has no scope-read command — `SS` is configuration only; the other four models remain unverified" |
| `SDD/03-project-definition.md:17` | "none documented → S-meter synthesiser" | "FTX-1: protocol has no scope read → S-meter synthesiser; other models unverified" |
| `SDD/04-system-context.md:33` | "**no scope interface exists** (undocumented waveform)" | "no scope-read command in the FTX-1 protocol (configuration only); other models unverified" |

不改 SDD 的理由很简单：SDD 的版本号由 `SDD/14` 首行权威、被 `release_check.py` 与测试盯着，改正文就得插一行版本记录。一次措辞修正不应该顺手掀动发布链。

## 结语

FTX-1 的技术选择可以一句话概括：**把功能做进盒子，把接口留给总线**。

SDR 与 DSP 分家，是为了让射频与音频各自演进；SPA-1 与 FC-80 独立成机，是为了让 10 W 的机身能长成 100 W 的台机；频谱只画给自己看，是为了省掉一条每秒几十帧的数据通路。每一处都把复杂度推给了硬件，把简单留给协议。

代价落在客户端身上。表计要自己轮询，通道身份要自己记，扫频要自己想办法，菜单要自己建表。这不是设计失误，是设计交换：它换来一台 10 W 的机身可以拆开、可以挂功放、可以进背包，而 CAT 面依然只是一条 38400 的串口。

我们做远程控制，站在这条交换的另一侧。**它省下的那条通路，得由我们来补。**
