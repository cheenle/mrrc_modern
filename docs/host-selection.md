# 跑 MRRC Modern 服务端，主机怎么选

面向"给一台机器当电台服务端"的选型备忘。结论先给，证据在后；每条数字都标了来源与可信度。

> 配套工具：`dev_tools/host_score.py`（零依赖，10 秒给一台机器打分）、
> `dev_tools/bench_mrrc.py`（要 repo + venv，出真正的 `% of one core`）。
> 设计文档：`docs/superpowers/specs/2026-10-06-w103d-radio-box-design.md`。

---

## 1. 结论：CPU 几乎不是选型依据

**服务端只吃一个核的一小部分。** 实测热路径在 Apple M2 上是 **1.53% of one core**
（`bench_mrrc.py`：rx 0.96% + spectrum 0.37% + tx 0.19% + state 0.01%），换算到一台
**2008 年的 Core 2 Duo** 也才约 18%。所以：

| 真正决定成败的 | 为什么 |
| --- | --- |
| **单线程性能** | 服务端是 Python（**有 GIL**），热路径跑在一个核上。核心数帮不上忙 |
| **USB 口数 ≥ 2** | 电台线一根 + 留一根给天调/U 盘。**这是最常见的翻车点** |
| **有线网口** | 服务端靠局域网访问（8888）。客户端每路只需约 60 KB/s，百兆都富余 |
| **7×24 的功耗与散热** | 它要常年通电放在电台旁边 |
| **可得性与价格** | 上面四条达标之后，这一条才是真正的决定因素 |

**别为 CPU 焦虑**：本页表里最慢的一颗（Atom D410）是唯一需要担心的，原因也不是跑分，
而是它**只有一个物理核**（见 §5）。

## 3. 口径与局限（读数字前先读这段）

1. **PassMark 是代理指标，不是我们的负载。** 它衡量的是通用 CPU 性能；本服务端是
   GIL 绑定的单线程 + 少量 numpy/C 代码。用它的**单线程**列排序是可靠的，
   绝对数值不要直接当成本。
2. **"服务端热路径"列是两级推导**：实测 1.53%（M2，`bench_mrrc.py`）→ 经本仓模型
   M2 ≈ 10× Pi 4 → Pi 4 ≈ 15% → 再经 J1900 ≈ 0.70× Pi 4 锚定 → 用上表的单线程比例换算。
   链条长，**带 ±30% 不确定度**，只用来分档，不用来比较相邻两名。
3. **样本数决定可信度**：N100 有 4111 个样本，R1305G 只有 28 个。
   **Pi 5（BCM2712）只有 4 个**——SBC 的 PassMark 条目是社区提交的，
   历史上见过超频结果，**不要拿它当选型依据**。
4. **CPU Mark 与单线程列不可互比**（PassMark 两者不同标尺，D410 就出现
   CPU Mark < 单线程）。跨 CPU 比同一列才有效。
5. **别忘了开销**：上表是热路径。真实运行还要加上 TLS、WebSocket 逐帧发送、
   GIL 争用、GC —— 大约再乘 **1.3–1.5**。

## 4. 那为什么还会遇到"跑不动"？

不是因为平均 CPU，而是这三件事：

- **只有一个物理核**（D410）。服务端的十几%全压在一个核上，而 systemd、journald、
  sshd、TLS 中断、录音编码**也排同一个核**。四核机器上"还剩 70% 容量"是假安全感。
- **顺序执行的窄核**（Bonnell 2010 / Silvermont 2013 / Cortex-A53）。平均吞吐够，
  但**调度抖动**差——典型症状不是"不出声"，而是状态行 `J:` 长期高于 500 ms，
  即"延迟慢慢涨"。这就是为什么下面同一档里我偏向乱序核。
- **老平台的内存带宽**（DDR2 单通道）。Python/numpy 比跑分更吃亏。

## 5. 逐台判定

| 平台 | 判定 | 一句话 |
| --- | --- | --- |
| **N100** | ✅ 最省心 | 单线程最高、6 W、四核、新机有保修。唯一"不用算余量"的 |
| **HP t640 / R1505G** | ✅ 二手首选 | **单线程与 N100 打平**（1822 vs 1879），15 W，企业淘汰量大、便宜 |
| **R1305G** | ✅ 可用 | 与 R1505G 同核但频率低 14%，8 W。板子来源比 R1505G 更少见 |
| **树莓派 4 / 5** | ✅ 官方基线 | 唯一有官方镜像的平台，零移植。单线程弱于上面三档但远够用 |
| **1037U** | ✅ 老 x86 最优 | 乱序核（Ivy Bridge），单线程是 J1900 的 1.4 倍，17 W |
| **Core 2 Duo T6400** | ✅ 白嫖可用 | 2008 年的机器单线程仍胜过 2013 年的 J1900。若是笔记本 = 自带 UPS + 屏幕 |
| **J1900** | ✅ 合适 | 四核、10 W、板子多且便宜。窄顺序核，靠四核补 |
| **W103D（S905L3A）** | ✅ 够用 | 约 0.57× Pi 4。**代价在部署**：要刷 ophub 镜像 + 专有内核（换内核即丢 WiFi） |
| **D525** | ⚠️ 可用但靠边 | 40–50% 单核。两个核修掉了 D410 的最大问题，但仍是窄顺序核 |
| **D410** | ⚠️ 勉强 | **只有一个物理核**，60%+ 单核占用，抖动风险高。不建议 |

**排序（单线程性能）**：
N100 ≈ R1505G ＞ R1305G ＞ 1037U ＞ Core 2 T6400 ＞ J1900 ＞ W103D ＞ D525 ＞ D410

## 6. HP t640 瘦客户机（专项）

**已知**：它用的就是本文表里的 **AMD Ryzen Embedded R1505G**（Zen+，2C/4T，2.4/3.3 GHz，
15 W，AES-NI + AVX2 + Vega 3 + DDR4-2400 双通道）。

> ⚠️ **可信度标注**：CPU 型号这个对应关系是**凭已知信息**给出的。本文编写时
> 尝试在线核实（PassMark 不列整机；DuckDuckGo 给人机校验页、Mojeek 403、
> HP 直连超时、Bing 返回无关结果）**全部失败**。买之前请以卖家的实机照片/规格页为准。

**瘦客户机形态对这个用途几乎是量身定做的**：

| 优点 | 说明 |
| --- | --- |
| 体积小、15 W 级、通常被动散热 | 放电台旁常年通电没负担 |
| **AES-NI / AVX2** | TLS 与 numpy 都走快路径（老 Atom/Celeron 全都没有） |
| DDR4 双通道 | Python/numpy 的内存带宽够 |
| 企业淘汰量大 | HP t640 / t630、Dell Wyse 一类成批出现在二手市场 |

**买之前必须确认的四件事**（我无法代你核实）：

1. **USB 口数 ≥ 2** —— 电台一根，另一根留给天调/U 盘
2. **存储形态**：有没有 SATA/M.2（多数瘦客户机只有 eMMC/M.2）。
   本服务端只要几百 MB，eMMC 就够；但**别指望装大盘录音**
3. **内存插槽与上限** —— 服务端只要 1 GB 就够，但确认能加到 4 GB+
4. **该型号有人装过 Linux** —— 瘦客户机 UEFI 偶有奇怪限制

> 模拟音频通常没有，**对本项目无所谓**：音频走电台自己的 USB 声卡。

## 7. 给一台机器打分

在候选机上（**不需要装任何东西**，只要 Python 3.9+；实测在 3.9.6 且无 numpy 的环境下可运行）：

```bash
scp dev_tools/host_score.py candidate:/tmp/
ssh candidate python3 /tmp/host_score.py
```

输出：这台机器做服务端一秒的 Python 工作量需要多少秒、相对参考机的倍率、
以及**估计的热路径占单核百分比**（带"舒适 / 够用 / 紧张 / 太慢"分档）。

它测的是真的东西：频谱帧解析（两段 850 元素的 `~b & 0xFF` 列表推导）+
归零打包（1700 次 `min`/`max`）+ 状态 JSON，速率与线上一致（频谱 30/s、状态 10/s）。
在参考机（Apple M2）上自测得 **0.37%**，与 `bench_mrrc.py` 实测的
spectrum 0.37% + state 0.01% 吻合——这就是它的自检。

**它测不到 libopus**（C 代码，脚本不随带库），所以用 Python 部分的比例去缩放
参考机的整体 1.53%。**是估计，不是实测**。盒子能跑起来之后，用
`dev_tools/bench_mrrc.py` 出真数。

即"核心宽窄比年代更重要"。
