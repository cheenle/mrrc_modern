# 远程协助（Call help）操作手册

面向**支持者**（你自己）与**客户**（用户）的两页纸。设计在
`docs/superpowers/specs/2026-10-12-remote-help-channel-design.md`，实现计划在
`docs/superpowers/plans/2026-10-12-remote-help-channel.md`。

## 它是什么

客户在自己界面上点一次，开通一条**限时**的 SSH 窗口；支持者在 hub 上用原生 `ssh` 连进去。
两端都在回环上：frps 只把代理口绑在 hub 的 `127.0.0.1`，实例侧的 SSH 只绑
`127.0.0.1`，**公网上没有任何 SSH 端口**。

三条结束路径：客户按「停止协助」、窗口到期、portal 上按「强制结束」。

## 客户怎么开

应用 → 遇到问题（Support）→ **远程协助** → 选窗口（30 分钟 / 60 分钟 / 3 小时）→
「开启协助」→ 页面上出现**用户名**与**口令**。客户把这两个念/发给支持者。

窗口到期自动关，**不会自动续**；口令只存在于那个应用的进程内存里：关掉即消失，不落配置、
不进日志、不进诊断包。

## 支持者怎么连

```bash
ssh www.vlsc.net                       # 先上 hub
ssh -p <协助端口> <用户名>@127.0.0.1     # 端口在 portal 的实例详情页上，可复制
```

口令向客户索取——**portal 不显示、不存储、不转发口令**。连上就是这台机器上的一个 shell，
权限等于 MRRC Modern 自己的权限（Windows/macOS 是当前用户，盒子/树莓派是 `mrrc`），
**不会提权**；盒子上需要 root 的动词仍走 `box_helper`。

## portal 上看到什么

实例详情页 → **远程协助**：

- 进行中：状态、端口、到期、最近心跳（客户在线/失联）、已连接次数、**那行 ssh 命令**（可复制）、
  「强制结束」。
- 已结束：结束原因（客户手动关闭 / 窗口到期 / 门户强制结束 / 口令被连续试错 / 心跳消失 / 应用退出）。

「强制结束」不立即生效：它置一个标志，实例在下一次心跳（≤20 秒）读到才断开。**实例离线时**
没有活着的会话可断，记录会由心跳超时标记为 `heartbeat_lost`，端口随之释放。

## 出问题时按这个顺序查

| 症状 | 先看 | 常见原因 |
| --- | --- | --- |
| 客户按了开启，界面报「这台机器还没接入 Cloud Hub」 | 应用的连接设置 | 该实例没有 portal 身份（callsign/token），先接入 Cloud Hub |
| 界面报「没有管理段（webServer）」 | 隧道配置里有没有 `webServer.port` | 实例是在管理段进生成器（2026-10-12）**之前**入网的，配置文件里从来没有这一段。**重启一次应用**即可自动补上（`cloud_hub.ensure_admin_segment` 在启动隧道前铸一个），然后再点一次「开启协助」 |
| 界面报 frpc 相关错误（且日志里是 `127.0.0.1:0`） | 同上 | 端口 **0** 不是网络问题，是「这份配置没有 `webServer` 段」的标记；按上一行处理 |
| 连进去了，「已连接」却一直是 0 | `/api/help/status` 的 `connections` | 2026-10-17 前的构建有这个缺陷：计数函数没有任何调用者（门只有事件，计数住在会话上）。已修（`SshHelpServer.on_disconnect` → `note_connection`），旧构建需要更新 `help_session.py` |
| portal 上看不到「进行中」 | portal 的实例详情页刷新；应用日志心跳 | 心跳没到 portal（网络/portal 未部署） |
| `ssh` 连不上 | `ssh -p <端口> 127.0.0.1`（确认在 **hub** 上敲） | 端口填错；或窗口已到期/被强制结束 |
| 连上但口令不对 | 客户重新读一遍口令 | 他可能改过；口令区分大小写 |
| 连续试错 5 次后自动关闭 | portal 上会显示「口令被连续试错」 | 有意的：本地进程也可能在扫这个端口 |

## 真机验收（盒子，**2026-10-17 已执行**）

平台：客户侧 W103D 盒子 `192.168.1.217`（armbian / `mrrc` / Cloud Hub `ba4eg`）+ 支持侧 `www.vlsc.net`。

| # | 判据 | 结果 |
| --- | --- | --- |
| 1 | 客户开启 | ✅ `/api/help/enable` 200，门户分配 **18818 / 18819**，窗口 30 分钟 |
| 2 | 支持者从 hub 连入 | ✅ `ssh -p 18818 help-960d@127.0.0.1`，交互式 shell，`id -un` = **`mrrc`**（uid 109，不提权） |
| 3 | 主入口不抖 | ✅ 协助全程 `https://ba4eg.mrrc.vlsc.net/` 稳定 302 |
| 4 | 客户停止 → 两端释放 | ✅ `close_reason: user`，hub 端端口不再监听，配置里的协助代理被摘掉，主代理保留 |
| 5 | 「已连接」计数 | ✅ `connections: 1`（修之前是 0，见下） |

**这一轮在真机上拓出并修掉的两个缺陷（都不是协议问题，是接线与既有状态）：**

1. **配置里没有管理段 → 每一次「开启协助」都失败**。盒子 `.217` 跑的是 v1.25.5，它的隧道
   配置写在 2026-10-12（`webServer` 段进入生成器）之前，而 `connect()` 不会为一个**已入网**
   的实例重写配置、`set_help_proxy()` 也不敢擅自铸一个（跑着的 frpc 不认）。于是报错是
   `frpc admin API unreachable on 127.0.0.1:0 after 3.0s` —— 端口 **0** 才是线索。
   修法：`cloud_hub.ensure_admin_segment()` 在**启动隧道之前**补一段（那是唯一安全的时机，
   frpc 只在启动时读配置），`set_help_proxy()` 遇到没有管理段时给一句能行动的话而不是去连 0 号端口。
2. **「已连接」永远是 0**。`HelpSession.note_connection()` 没有调用者：SSH 门（`SshHelpServer`）
   只有 `on_event`，计数却住在会话上，两边没有接线；单测直接调 `note_connection()`，所以看不见。
   修法：门在会话结束时回调 `on_disconnect` → `build_session()` 把它接到 `note_connection()`，
   并补一条**走接线本身**的测试（真 paramiko shell 会话 → `status()["connections"] == 1`，
   探针 exec 不计）。

## 真机验收（**2026-10-12 已执行**）

平台：客户侧 macOS（本机 `bg1sb`，真证书真隧道）+ 支持侧 `www.vlsc.net`（生产门户）。
前置三件事都已做：门户部署（4 个文件、md5 与本地逐一相同）→ 实例重新接入（写出 `webServer` 管理段）
→ 五条判据逐项跑。

| # | 验收项 | 结果 |
| --- | --- | --- |
| 1 | 客户开启 | ✅ `/api/help/enable` 200，门户分配协助口 **18813**，界面拿到用户名/口令/30 分钟窗口 |
| 2 | 支持者连入 | ✅ 从 hub 抓 `127.0.0.1:18813` 得到 **`SSH-2.0-paramiko_5.0.0`**（证明 frps 回环→实例这条链）；本地用真口令登录并跑通命令；**交互式 `zsh -l` 会话也跑通** |
| 3 | 主隧道不抖 | ✅ 协助全程实例入口稳定 **302**（正常未登录跳转），无 502 |
| 4 | 三条关闭路径 | ✅ 门户强制结束：hub 上 `POST /help/revoke`（`X-Portal-Token`）→ **20 秒内**心跳读到 → 实例 `closed / portal`、口令字段消失、协助代理摘掉、**本地与 hub 两端端口都不再监听**；门户记录与审计落上（`help_requested → help_heartbeat → help_revoke_queued → help_closed portal`，记录里**没有口令字段**）。客户手动关与到期由单测覆盖 |
| 5 | 权限边界 | ⏳ 只在本机验了"app 进程权限、不提权"这一半；**盒子/Pi 上的 `mrrc` 边界仍待真机** |

**这一轮拓出并修掉的真缺陷（六处，全部只在意料之外的地方出现）**：

1. `reload_frpc` 用了 POST，真 frpc 回 **405**（它要 GET）—— 单测的假服务端只实现了 do_POST，
   **一个会同意任何请求的 mock，也会同意一个 bug**；
2. `connect()` 每次重连都新铸管理端口，而 frpc 只在启动时读一次配置 → 重连后两者分叉
   （配置 53235 / 活着的 frpc 53189），reload 打空；改为**管理段只铸一次、之后复用**；
3. `channel.get_terminal_type()` 不存在（term 在 pty 回调里）—— 交互式会话从没被驱动过；
4. `check_channel_shell_request` 在 transport 线程上同步跑泵 → 成功应答发不出、输入收不到，
   会话在**任何字节流动之前**就死；泵改为独立线程；
5. `TunnelProcess.start()` 按占位符 `pending.toml` 清扫旧 frpc（构造时用的路径），
   真实路径是 `connect()` 之后才塞进来的 → 上一次的 frpc 活着占着代理名（实测两个 frpc 打架）；
6. （自查）按切片替换 `reload_frpc` 时误删了三个门户函数，而当时只跑了单文件测试。

## 已知边界（未验，别写成"已验证"）

- `frpc reload` 在仓库钉的 **frp 0.71.0** 上的真实行为（上面第 3 条就是验它）；
- Windows 上 paramiko 起 `powershell.exe` 的 pty 行为（换行、颜色、`Ctrl-C`）；
- macOS 上从 launchd 启动的会话环境（PATH 与可交互性）；
- 盒子上 `mrrc` 用户的实际能做/不能做清单（第 5 条的结果要回填到这里）。

**离线已经钉住的**（`tests/test_help_end_to_end.py`）：门户协议字段、隧道配置的加/删与
reload 的认证、真 paramiko 客户端用真口令连入并执行命令、错口令被拒、关闭后端口不再接受连接。
