# W103D 初始化热点 + 配置管理页 — 设计

> 状态：**待审**（本文档通过后才出实现计划）
> 前序：`docs/W103D_GUIDE.md`（刷机与配置指南）、`2026-10-06-w103d-radio-box-design.md`（盒子部署设计）

---

## 1. 问题：一个鸡生蛋

盒子的首次配置需要**同时**具备两样东西，而它们互为前提：

```
要配 WiFi  ──需要──▶ 能操作盒子 ──需要──▶ SSH(要有网) 或 HDMI+键盘(要有显示器键盘)
```

盒子的第一版设计（设计文档 §3）默认了操作者手边有网线或键鼠。**实际不成立**：盒子买回来可能
只有一台手机，或者放在电台旁边根本不想接显示器。

## 2. 目标 / 非目标

**目标**

1. 盒子**在没有任何可用网络时**，自动开一个**开放热点**；手机/电脑连上即可完成初始化。
2. 初始化只需三件事：**设 Web 口令、连 WiFi、确认电台型号**。
3. 同一套页面在配置完成后**继续可用**，作为**完整配置管理页**（用户选定方案 B）。
4. 现有 MRRC 界面里的设置**保留不动**——**两个界面，一个配置层**。

**非目标**（明确不做，避免范围蔓延）

- **不做 captive portal**（不做 DNS 劫持/自动弹窗）——见 D-6 的替代做法。
- **不重做 Cloud Hub 的 apply/connect 流程**——它自带状态机，页面只显示状态并触发。
- **不替代 NetworkManager**，不自己写 hostapd 配置。
- **不做 AP+STA 并发**（单射频，见 D-3）。
- 不做 Captive 门户式的全屏引导，不改现有设置界面的既有行为。

## 3. 需求

| | 需求 | 验收判据（可测） |
| --- | --- | --- |
| R1 | 无网时自动起开放热点 | 拔掉网线 + 无已保存 WiFi → 热点在就绪后出现；插上网线 → 热点消失 |
| R2 | 引导页解掉鸡生蛋 | 从热点网段访问 `/setup` **无需口令**即可设口令；配好后**同一路径需口令** |
| R3 | 完整管理页 | §4 字段表里标 ✅ 的项都能读、能改、改完能生效 |
| R4 | **两个界面同一配置层** | 两个入口写同一个文件、走同一函数；并发改不丢字段（整文件不可 last-write-wins） |
| R5 | 安全围栏 | 热点**只在无其他网络时存在**；引导分支**只对热点网段开放**；每次引导开放都留日志 |
| R6 | 可诊断 | 热点起没起、WiFi 连没连上、失败原因，都能在 `/manage` 与 `journalctl` 看到 |

## 4. 字段表（用户已确认）

### 4.1 引导页（三件，仅首次窗口）

设口令 · 连 WiFi · 确认电台型号（等同 `mrrc-radio use`，保留"换机型清旧串口"的行为）

### 4.2 管理页

| 字段 | 生效 |
| --- | --- |
| `MRRC_RADIO_MODEL` / `MRRC_SERIAL_PORT` / `MRRC_BAUD_RATE` | 走 `mrrc-radio` 的逻辑（探测+清旧串口），非直接写 |
| `MRRC_SCOPE_PORT` / `MRRC_SCOPE_BAUD` | 重启服务 |
| `MRRC_AUDIO_RX_DEVICE` / `MRRC_AUDIO_TX_DEVICE` | 重启服务；**下拉项从 `arecord -l` / `aplay -l` 实读**，不许手敲 |
| `MRRC_ATR1000_HOST` / `MRRC_ATR1000_PORT` | 重启服务 |
| `MRRC_RECORDINGS_DIR` / `_BITRATE` / `_MAX_SESSION_MIN` | 重启服务 |
| `MRRC_SESSION_METRICS_INTERVAL_S` / `_WINDOW_S` | 重启服务 |
| `MRRC_FTDI_LIB_DIR` | 重启服务 |
| `MRRC_WEB_PORT` / `MRRC_WEB_HOST` | 重启服务；**改端口要明确提示新地址**（当前连接会断） |
| `MRRC_LISTEN_PASSWORD` | 重启服务 |
| **`MRRC_ALLOW_UNVERIFIED_TX`** | 见 D-5 |
| **`MRRC_PTT_MAX_TX_SECONDS`** | 见 D-5 |
| `MRRC_REMOTE_SESSION_TX_HEARTBEAT_S` | **只读**（Cloud Hub 自动写） |

### 4.3 明确排除（不进页面）

| 字段 | 理由 |
| --- | --- |
| **`MRRC_CONFIG_FILE`** | ⚠️ **D-11 的载荷**：systemd 单元钉着它；页面能改它 = 把"UI 显示已连接、上游 TLS 校验失败"那个静默故障挖回来 |
| `MRRC_NO_CONFIG_FILE` / `MRRC_MEM_FILE` / `MRRC_CQ_FILE` / `MRRC_LOG_DIR` / `MRRC_FT4222_CLK_DIV` / `MRRC_SUPPORT_URL` | 内部/高级 |

### 4.4 两个不是普通字段的东西

- **WiFi**：走 NetworkManager，**不走 env**——这是全项目唯一一条不同的写入路径（见 D-4）。
- **Cloud Hub**：是流程不是字段，只做"显示状态 + 触发"，不重做状态机。

## 5. 设计决策

### D-1 页面并进现有服务器（否决独立 setup 服务器）

**决定**：`/setup` 与 `/manage` 是**现有 FastAPI 应用的普通路由**。

**权衡**：独立轻量服务器在 AP 期间暴露面更小，但需要**第二套配置写入路径**——两个 UI 各写 env 文件，
整文件 last-write-wins 会互相覆盖，还会读到陈旧值。为了省一点暴露面换来长期的正确性风险，不划算。

**推论**：AP 模式下用户访问的就是 `https://<热点网关>:8888`。服务器本来就在跑，AP 不需要额外进程。

### D-2 热点用 NetworkManager，镜像要加 `dnsmasq`

**决定**：`nmcli device wifi hotspot`，加 `dnsmasq` 进镜像的装机清单。

**依据（实测）**：镜像里 `mac80211`/`cfg80211`/`wpa_supplicant`/`iptables` 都在，
**`dnsmasq` 缺**——而 NM 的 hotspot/shared 模式靠它发 DHCP 与 DNS。`hostapd` 非必需（NM 用 wpa_supplicant 做 AP）。

### D-3 单射频 → AP ↔ STA **切换**，不做并发

**决定**：热点与连网二选一，配完**切**过去，不试图同时。

**依据**：MT7663S 是一颗射频（WiFi 与蓝牙同一颗芯片、走 SDIO）。并发模式多数芯片不支持，
**是否支持要真机验证**（见 §8 边界）。切换是 IoT 设备的标准做法。

### D-4 唯一的新写入路径：nmcli 适配层

**决定**：`MRRC_*` 全部走**现有配置层**；WiFi 走一个**薄适配层**（起热点 / 扫描 / 连 / 断开 / 查状态）。

**约束**：这个适配层**只碰 NetworkManager 的连接配置**，绝不碰 `/opt/mrrc_modern/env/mrrc.env` ✅
（反过来，配置层也绝不碰 NM）。两个域各有唯一写入者，这是 R4 能被验证的前提。

### D-5 安全字段：门禁与上限

| 字段 | 处理 |
| --- | --- |
| `MRRC_ALLOW_UNVERIFIED_TX` | **只读显示 + 当前值**；要改必须**两步显式确认**，且页面必须把"这意味着什么"写出来（8 个未验证机型：指令表来自 Hamlib/手册，不是真机实测；开着就可能在没有实测过的频率/功率语义上发射）。**默认呈现为"关"，且不做任何"一键开启"的快捷方式** |
| `MRRC_PTT_MAX_TX_SECONDS` | 可改，但**调高或清空**要显式确认（防线②被削弱） |
| `MRRC_REMOTE_SESSION_TX_HEARTBEAT_S` | 只读——防线①由 Cloud Hub 写 |

**理由**：AD-019 / NFR-067 是这套系统里少数的**安全不变量**，而网页开关是最容易把不变量变成事故的形态。
现有测试已经断言"profile 里出现 `=1` 就红"，这条设计要与之同向，不能相反。

### D-6 「未配置」的判据，以及引导分支的闸门（**本设计的关键点**）

**热点什么时候起**——判据是**网络状态**，不是"首次开机"：

```
起热点  ⟺  没有可用上行：网线无链路  且  没有已保存且能连上的 WiFi
```

**引导分支（免口令设口令）什么时候开放**——闸门是**网络路径**：

```
免口令开放  ⟺  请求来自热点网段
```

**为什么这样就够了**：配置完成后热点**关闭**，那个网段**不复存在**，因此免口令分支**自然失效** ✅
——不需要"是否已配置"的标记，也就不会有"标记写失败导致永久敞开"这类故障模式 ✅

**围栏（三条叠加）**

1. **只在没有其他上行时起热点**（有网线/WiFi 就永不起）
2. **首个会话超时**：热点起后 N 分钟无人完成引导 → 自动关闭（默认 30 分钟，可配）
3. **引导期间每次访问写日志**（谁在什么时候连上、从哪个 IP），`/manage` 里能看

**超时之后怎么再进来（v1 的恢复路径）**：**断电重启**。开机那一刻若仍然没有可用上行网络，热点会重新起来、
计时器重新计时 ✅ 所以「错过窗口」不会让盒子变砖——只要还没配好网，每次上电都重新给一次机会。
*（长按复位孔强制重开更省事，但 v1 不做，留给后续。）*

**残留风险（诚实记录）**：热点开放期间，**同一网段内的人可以先下手设口令接管盒子**。
WiFi 半径十几米，公寓楼里邻居可能在里面。三条围栏把窗口压到"你主动插电后、且附近没有网络"的
那几十分钟，但**不能消除它**。缓解手段：HDMI 上同时印出引导地址（你不必依赖热点）、
以及 §9 里预留的"长按复位孔重新开放"作为恢复路径。

### D-7 `MRRC_CONFIG_FILE` 绝不进页面

见 §4.3。这条单独列出是因为它是**唯一一条"改了会静默坏掉、且很难查"的字段**。

### D-7.5 引导页不必等配置层（2026-10-08 实现前摸底，**改变交付顺序**）

摸底发现：**服务端已经有一条写配置的现成通道** —— `server.py:3216` 会写
`updates["MRRC_WEB_PASSWORD"]`，经 `cloud_hub._write_config(_config_file_path(), {...})` 落盘。
它是**既有的**写入者，不是新长的第二份。

> **2026-10-09 实现时更正**：落盘那一步走的其实是
> `first_run.update_env_file(_config_file_path(), updates)`（`/api/setup` 处理函数里，
> 紧跟在上面那行赋值之后），**不是** `cloud_hub._write_config`。后者是**另一处**写入者，
> 只被 `_ensure_strong_password()` 用来保存它自己生成的随机口令。结论不变（既有通道确实
> 存在，向导照抄它即可，D-8 不是硬依赖），但"要收敛的写入者"清单里这两条是**两个不同的**
> 函数——向导复用前者，D-8 需要同时收敛两者。

**推论**：引导页"设口令"可以直接调它 ✅ 所以**配置层重构（D-8）不是热点+向导的硬依赖**，
只是一个"把 7 个写入者收敛成一个"的整洁目标。

**交付顺序因此再修一次**（操作者要求"赶紧做现在的 103D"）：

| 序 | 内容 | 依赖 |
| --- | --- | --- |
| **1** | **热点 + 最小向导**（设口令 + 连 Wi-Fi） | 只依赖既有写入通道 ✅ **已交付**（实现计划 `docs/superpowers/plans/2026-10-08-w103d-setup-hotspot-wizard.md`，2026-10-09） |
| **2** | 配置层统一（把 7 个写入者收敛） | 独立价值，不与 1 互锁 |
| **3** | 完整管理页 `/manage` | 依赖 2 |

⚠️ **必须同时处理的**：`server.py:907` 在口令为空时**会自动生成一个随机口令**并写回。所以"默认空口令"
**实现不了**（空了反而生成随机的）。替代做法：引导页在免口令窗口内直接**让操作者设一个**，
在此之前不依赖"已知口令" ✅



> **2026-10-08 补充（实现前摸底）**：这条比原先写的更严重。项目里**已经有 5 处在各写各的 env 文件**：
> `linux/first_run.py:170` 与 `macos/first_run.py:221` 的 `update_env_file()`（**同一函数的第二份**）、
> `packaging/box/` 与 `packaging/rpi/` 的两份 `firstboot_wrapper.py`、以及 `install.sh`（shell）。
>
> 所以 D-8 不是"新增时要共用"，而是**先把已有的写入者收敛成一个**。本期的交付物因此是
> **一个统一写入层 + 把 5 个调用点搬过去**，而不是新建一个写入者。这也让一期的价值更明确：
> 就算管理页永远不做，收敛这 5 份本身就是净收益。



**约束**：两个入口必须调用**同一个写入函数**，该函数：

1. 读现有 env → 合并本次改动 → 原子写回（**不是整文件覆盖**）
2. 保留不属于自己的键（口令、证书路径、Cloud Hub 写的键）
3. 写后按需重启服务，并**把结果回报给调用者**

**验收**：一个测试，同时经两个入口各改一个字段，断言两个改动都在、且第三个字段没丢。

## 6. 数据流

```
开机
 └─ mrrc-setup-ap.service
     ├─ 有网线链路 或 有能连上的 WiFi ──▶ 什么都不做（并确保热点关着）
     └─ 都没有 ──▶ nmcli device wifi hotspot（开放）
                   └─ 启动计时器（默认 30 min）
用户手机连热点 → 打开 https://<网关>:8888  （HDMI 上也印这个地址）
 └─ /setup：免口令（因为来自热点网段）
     ├─ 设口令 ──▶ 写 env（配置层）
     ├─ 选 SSID + 输密码 ──▶ nmcli 连（nmcli 适配层）
     │   ├─ 成功 ──▶ 切 STA、关热点、计时器停
     │   └─ 失败 ──▶ 回到热点 + 把失败原因显示出来（**不能静默回去**）
     └─ 确认电台型号 ──▶ mrrc-radio use
引导完成 → /setup 的免口令分支随热点一起消失；/manage 走正常鉴权
```

| 组件 | 形态 | 职责 |
| --- | --- | --- |
| `mrrc-setup-ap.service` | 新 systemd 单元，**常驻小脚本** | 判定 → 起/停热点 → 计时器 → 对外提供状态 |
| | *(为什么不是 oneshot：`/manage` 要显示热点开着没、还剩多久；oneshot 跑完就没了，状态无处可问)* | |
| `/setup` 路由 + 页面 | 现有应用 | 引导三件 |
| `/manage` 路由 + 页面 | 现有应用 | §4.2 字段 |

| `net_wifi` 适配层 | 新，薄 | 封装 nmcli：热点/扫描/连/状态 |
| `box-overlay.sh` | 改 | 装机清单加 `dnsmasq` |

## 8. 测试

- **配置层**：并发/连续改两个字段不丢第三个；排除字段不可写；写后重启被调用
- **闸门**：模拟"来自热点网段"与"来自其他网段"的请求，断言免口令分支只在前者开放
- **引导流程**：WiFi 连成功 → 切 STA 且关热点；连失败 → 留在热点且带错误信息（**负例必须测**）
- **安全字段**：`MRRC_ALLOW_UNVERIFIED_TX` 的写入必须经过两步确认（源码级守卫，与既有
  `test_box_profiles` 的"=1 就红"同向）；`MRRC_CONFIG_FILE` 不在任何可写字段集合里
- **热点判定**：有网线/有 WiFi 时不起热点（用假 `nmcli` 输出驱动）
- **不做**：真机 WiFi 行为（见下）

## 8.5 交付顺序（2026-10-08 按操作者反馈调整）

**操作者明确了一条产品期待**：*"刷完启动就应该有 Wi-Fi 热点、无密码，连上就可以设置。"*
这句话把**热点 + 最小向导**从"二期"提到了**首次可用的前提**——没有它，只有一台手机的人
根本无法开始。顺序因此重排：

| 序 | 内容 | 为什么是这个位置 |
| --- | --- | --- |
| **1** | **配置写入层统一（D-8）** | 向导"设口令"必须走唯一的写入层，所以它是硬依赖 |
| **2** | **热点 + 最小向导**（设口令 + 连 Wi-Fi + 确认机型） | **这才是"连上就能设置"的最小闭环**，也是操作者要的那个体验 |
| **3** | 完整管理页 `/manage` | 价值仍在（一次能改全部设置），但**不再是首次可用的前提** |

**为什么不是"先只做热点"**：热点单独存在时，连上只能到达现有 MRRC 界面，而它要一个用户还不知道的口令
——**等于把鸡生蛋换了个位置**。所以热点必须与"设口令"同批交付。

**2 的验收判据（操作者可判）**：刷完盘、不插网线、不接键盘，只拿一台手机——
开机后能在 Wi-Fi 列表里看到盒子开的热点，连上后打开页面**无需口令即可设口令并选 Wi-Fi**，
成功后盒子切到 STA 并关掉热点。

## 9. 风险与未决

| | 风险 | 处理 |
| --- | --- | --- |
| R-1 | **MT7663S 的 AP 模式是否可用，未在真机验证** | 设计上不依赖它成立：热点起不来时 HDMI 控制台 + `nmtui` 仍可用（指南 §9）。真机验证列为验收项 |
| R-2 | 开放热点窗口被邻居抢设口令 | §D-6 三条围栏；残留风险已记录 |
| R-3 | 重启服务会打断正在进行的会话 | 页面明确提示；引导阶段本来没有会话 |
| R-4 | 两个界面并存带来的认知负担 | 用户已接受；靠 R4（同一配置层）保证不会不一致 |

**R-1 状态（2026-10-08 操作者决定：先按"能用"做）**：这条假设本机无法验证，而它会挡住整条链，
所以采用它 —— 但只配一个**失败时说得清**的实现，不配"祈祷"。

| 项 | 内容 |
| --- | --- |
| 真机验证（一条命令） | `nmcli device wifi hotspot con-name t ssid t && nmcli connection down t` —— 手机能看到 `t` 即成立 |
