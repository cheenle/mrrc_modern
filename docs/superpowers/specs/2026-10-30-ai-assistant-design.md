# 产品 AI 助手（网页内答疑 + 反馈归并）设计

- **日期**：2026-10-30
- **状态**：设计定稿，待实现
- **范围**：盒子/桌面实例的**网页客户端**里的问答入口 + 一个中央知识服务。**不含**微信/企业微信
  任何通道（见 §1.1 的取证）。
- **相关代码（拟新增）**：`assistant_client.py`（盒子侧薄客户端）、`server.py` 三条路由、
  `static/assistant.js` + `static/support.html` 的菜单入口、`tools/assistant_gateway/`（中央）、
  `dev_tools/make_assistant_kb.py`（知识库生成）
- **相关约束**：所有出站请求必须走 `net_tls.urlopen()`（`tests/test_tls_trust_store.py` 的 AST 守卫）；
  静态资源 `?v=` 手工 bump；两个受保护的前端文件不得改动（本设计**不碰** `ft710_main.js`/`ft710_ui.js`）

---

## 1. 背景

### 1.1 为什么不在微信群里做（取证结论）

原本的设想是「微信群里的 AI 分身」。查过企微官方文档与开发者社区后，这条路在**外部客户群**上
被平台边界封死：

| 能力 | 客户群（含个人微信用户） |
| --- | --- |
| 群机器人 | **外部群不能添加任何机器人** |
| 智能机器人（大模型） | **只进内部群** |
| 消息推送回调 | 不支持外部群，无回调 |
| 会话内容存档 | 唯一可读到群消息的途径，**付费**（服务版 900 元/人/年，2026-01-22 起） |
| 群内发消息 | 仅「客户群群发」，需成员确认，**每群每天最多 1 条** |

即：**客户群里不存在「自动答话的机器人」这个形态**；能自动的只有「读」（付费），回群永远要人。
而在**个人微信群**里连「读」都没有官方途径。

结论：把交互放回**自己的网页客户端**——零通道风险、零接口费、零迁移成本。

### 1.2 现状里可复用的东西

`support_autopilot`（分类 + 共性）、`support_board`（看板 + 排期）、`support_answers`（答复页）
已经把「反馈 → 判断 → 沉淀」这条链跑通了。本设计新增的只是**信源**（网页问答）与**出口**
（当场答疑），判断与沉淀复用同一套数据。

## 2. 目标 / 非目标

**目标**

1. 客户在网页里就能问，**多轮**，答案带出处；产品知识跟不上时明确说「待确认」。
2. 每一条问答都留存，作为**产品迭代与反馈归并**的原料。
3. 检索优先，模型只负责「组织语言」或「兜底」；成本与幻觉都被压住。
4. 客户看得见自己要交出去什么（白名单状态摘要）。

**非目标**

- 不做微信/企微通道（§1.1）。
- 不做语音输入、不做图片理解、不做 agent 式的多步工具调用。
- 不让助手读客户的录音、呼号、频率、诊断包原文。
- 不做流式输出（首发非流式，稳定后再评估 SSE）。
- **本规格只覆盖客户侧**（①知识层 + ③中央生成 + ④网页入口）。运营侧那套「值班人批量粘贴群消息
  → 切条判类 → 归并进看板」是**下一份规格**，复用同一个网关与会话库，不在本文展开。

## 3. 架构：薄客户端 + 中央大脑

```
客户在网页里问（可多轮）
   │  UI 明示「本次会发送：型号 1.28.22 · 串口已连 · 声卡正常」
   ▼
POST /api/assistant/ask {conversation_id, message}     ← 盒子：只做转发，不带任何知识
   ▼
中央知识服务（自建）
   ├─ 会话存储（多轮上下文 + 全量问答留存）
   ├─ ① 规则层（不调模型、不扣配额）
   ├─ ② KB 检索（不扣配额，命中即用条目事实）
   ├─ ③ 兜底生成（扣配额，标「AI 生成 · 待确认」）
   └─ 审计（谁、问什么、命中哪条、是否兜底、耗时、tokens）
   ▼
答案 + 出处 + 徽标 → 返回盒子渲染
```

**知识库集中在中央，盒子不留副本**（用户决定，2026-10-30）。直接后果：

- **断网 = 没有助手**。面板必须直说：「助手需要联网；本地不留知识库。可以先提 🐞 诊断包。」
- 每次提问都要出网一次（但**只有 ③ 计费**，①② 在中央本地完成）。

| 单元 | 位置 | 职责 | 依赖 |
| --- | --- | --- | --- |
| `tools/assistant_gateway/` | 中央服务器 | KB、检索、模型、会话存储、审计、配额 | 模型 API |
| `dev_tools/make_assistant_kb.py` | 本仓库 | CHANGELOG / 看板 / 答复页 / FAQ → `assistant_kb.json` | 无 |
| `assistant_client.py` | 盒子 | 白名单状态摘要、转发、离线话术、响应整形 | `net_tls` |
| `POST /api/assistant/ask\|clear\|status` | `server.py` | 鉴权、限速、10 s 超时 | `assistant_client` |
| `static/assistant.js` | 前端 | 多轮气泡、出处、徽标、有用/无用、清空会话 | — |

## 4. 状态摘要：白名单与守卫

`assistant_client.state_summary()` 返回**固定键集**的扁平 dict：

| 字段 | 例 | 用途 |
| --- | --- | --- |
| `model` | `ft710` / `ftx1` | 一半问题按机型分叉 |
| `version` / `fixpack` | `1.28.22` / `FP18` | 「我这版修了没」 |
| `serial_connected` | `true/false` | 「为什么没频谱 / 不能调」 |
| `audio_rx_open` / `audio_tx_open` | `true/false` | 「没声音」 |
| `last_errors` | 最多 3 条，**归一化**：错误码 + 一句人话（去路径、去呼号、去频率） | 定性「哪一类坏」 |
| `platform` / `ui_lang` | `linux-arm64` / `zh` | 路径与话术 |

**三条守卫，都要有测试**：

1. **键集断言**：键集合**精确等于**上表 —— 想加字段必须改测试；
2. **黑名单扫描**：序列化后的 JSON 不含 `callsign|freq|recording|auth-token|MRRC_WEB_PASSWORD|/dev/`
   （用真实值构造，不空跑）；
3. **体积上限**：整个摘要 ≤ 2 KB。

界面在发送前**原样列出这几行**（可折叠）。

## 5. 判定顺序与配额

```
① 规则层（不调模型、不扣配额）—— 3 条确定性诊断
   串口没连 · 声卡没开 · 版本低于该问题的修复版本
   → 模板答案 + 一句可执行动作

② KB 检索（不扣配额）
   命中 = top1 分数 ≥ **0.72** 且 top1 与 top2 相差 ≥ **0.04**，且条目的 applies_to
   覆盖本机 version/model（两条默认值都待真实提问校准，见 §11）
   → 模型只按条目组织语言，事实必须来自条目

③ 兜底生成（扣配额，默认 20 次/台/天）
   → 答案带「AI 生成 · 待确认」；配额用完回落 ② 的低分候选 + 「没查到，建议提 🐞」
```

**多轮上下文**：最近 **3 轮**原文 + 更早轮次的**一句话摘要**（服务端维护），上限 6 KB。

**硬规矩**：②/③ 的答案里，任何事实性断言都必须能指回条目 id（渲染显示「出处」）；
指不回去的句子不许出现 —— 网关做后置校验（版本号、命令、配置项与条目比对），
校验不过即降级为「待确认」。

## 6. 接口契约

```http
POST /v1/assistant/ask
X-Mrrc-Instance: <安装时生成的匿名实例 id，非呼号>
{ "conversation_id": "…|null", "message": "为什么没频谱",
  "state": { …§4 白名单… }, "lang": "zh", "client": "1.28.22" }

200 → { "conversation_id": "…", "turn_id": "…", "answer": "…",
        "citations": [{"id": "kb-1.28.22-cq", "label": "1.28.22 · CQ 发射节拍", "url": "…"}],
        "mode": "rule|kb|generated", "needs_confirm": false,
        "degraded": "" }
```

盒子本地：`POST /api/assistant/ask`（补 state 后转发，**10 s 超时**）、`POST /api/assistant/clear`
（删本实例会话）、`GET /api/assistant/status`（是否开通 + 今日剩余配额）。

**出站必须走 `net_tls.urlopen()`** —— 绕过它等于重演「某台机器证书库为空 → 全部外发失败」。

**模型端点**：网关侧一个 **OpenAI 兼容** 的 HTTP 接口，默认指向 DeepSeek（境内、便宜、
本仓已有使用先例），可用 `MRRC_ASSISTANT_MODEL_URL` / `_MODEL` 换成任何兼容端点。
模型选择是网关的配置，不是盒子的配置 —— 盒子永远不知道用的是哪家。

## 7. 存储与留存

| 表 | 关键列 | 用途 |
| --- | --- | --- |
| `conversations` | id, instance_id, lang, created, updated | 多轮归属 |
| `turns` | id, conv_id, role, content, mode, citations, needs_confirm, tokens, ms, ts | 留存与迭代原料 |
| `kb_entries` | id, kind, title, body, keywords, applies_to{version_min, models}, source_id | 检索 |
| `feedback` | turn_id, useful, note, ts | 「有用吗」→ 反哺 KB |

- **留存 180 天**硬删（定时任务），`conversations` 随之清空；
- 客户「清空会话」→ 按 `conv_id` **立即硬删**；另提供按 `instance_id` 整体删除；
- **入库只有**：问题原文、白名单 state、答案与出处、徽标、反馈；
- **永不入库**：任何白名单之外的机器数据；
- 看板/答复页只引用**归并后的共性**，不引用原话。

## 8. 错误处理矩阵

| 情况 | 行为 | 客户看到 |
| --- | --- | --- |
| 连不上中央（1.5 s 内失败） | 立即失败，不转圈重试 | 「助手需要联网；本地不留知识库。可以先提 🐞 诊断包。」 |
| 中央 5xx / 模型超时 | 有 KB 低分候选就用 | 「没把握，最接近的是：…（待确认）」 |
| 答案指不回出处 | 强制降级 | 「AI 生成 · 待确认，建议核对出处」 |
| 配额用完 | 纯检索 | 「今天的自动答疑已用完，以下是知识库里的相关条目」 |
| 鉴权失败 / 未开通 | 面板置灰 | 「助手未开通，请联系维护者」 |
| 会话过期/被删 | 新开一轮 | 无感 |

**隔离**：助手不得影响电台链路 —— 独立 HTTP、独立超时；禁止在 `_audio_*` / PTT / CAT 循环里
同步等待它。

## 10. 上线、回退与度量

1. 先上中央服务（`curl` 可验三条路径）；
2. 再发盒子版本（☰ 菜单「AI 助手」+ 面板）；
3. 开关：`MRRC_ASSISTANT=off`（面板不出现、路由 404）、`MRRC_ASSISTANT_URL`（指向网关）、
   网关整体 `503`（所有盒子当场灰态，**不发版**）。默认**开**。

**四个数**：命中率、兜底率、「无用」反馈率、每台日均提问。
目标：**兜底率 < 30%**（否则知识库没跟上发布）、**无用率 < 10%**。

**与发布绑定**：`make_assistant_kb.py` 产物进 `release-artifacts.json` 并加一条规则 ——
**CHANGELOG 新增一条，KB 必须多一条**，否则「发了版但助手不知道」会像下载卡 SHA 一样静默漂移。

## 11. 风险与未决

- **中央服务是新的一台**：可用性直接影响助手（但不影响电台）。需要与 support receiver 同机部署，
  并纳入现有的 nginx/证书体系。
- **模型成本未知**：先按「未命中 20 次/台/天」封顶，上线两周后用真实数据调。
- **KB 质量是本设计的命门**：`make_assistant_kb.py` 的条目质量决定兜底率；先做一版，
  用真实提问回归。
- **未决**：§5 的相似度阈值与 §10 的配额初值都需要真实数据校准，规格里先给默认值。
