# Xiegu G7250 backend — design (2026-11-07)

Add the **Xiegu G7250** (协谷 G7250, 100 W HF/6 m direct-sampling SDR, announced
2026-07-22, first shipments December 2026) as a selectable radio model, with no
unit in hand — the same offline-specification path the IC-705/IC-7610/IC-7760
round used (SDD V2.41).

## 1. Why this is not a copy of an existing family

The G7250 is the first radio behind this server that is **neither Icom, nor
Yaesu, nor Kenwood**. It has two independent control surfaces and this design
had to decide what each one is for.

| Surface | What it carries | Evidence |
| --- | --- | --- |
| **USB serial (CI-V)** | CAT (frequency/mode/levels/meters/CW), PTT, ATU | Icom-style CI-V framing — Xiegu's documented behaviour for X6100/X6200/G90 [X6]; the G7250's own CI-V document does not exist yet |
| **LAN (UDP)** | IQ baseband only — **no CAT, no PTT** | third-party reverse engineering, hardware-tagged [RE]: radio listens on 50002 for a 14-byte tune frame, pushes 768-byte int16 I/Q payloads to 50001 (48 kS/s = ±24 kHz) |
| **USB audio** | RX/TX audio (built-in sound card) | product documentation ("内置声卡 / built-in USB sound card") |

Upstream status checked 2026-11-07 — **none of them supports this radio**:
wfview `master` `rigs/` has no Xiegu file at all (31 rig files, no G7250);
wfview's "supported radios" page lists only X6100/X6200; the wfview forum search
returns zero hits for `7250`; Hamlib `master` `rigs/icom/xiegu.c` stops at the
X6200; GitHub has exactly one G7250 project, which is simulator-only on the
CI-V side. So there is no implementation to copy and every CI-V table here is
a documented assumption until a real unit answers.

## 2. Decisions

**D1 — reuse the shared CI-V core, add a new package.**
`backends/xiegu/` imports `civ_codec`/`civ_controller` from
`backends/ic7300/` (whose directory name is historical — it hosts the shared
CI-V core) and reuses `CivModelProfile` unchanged. Directory boundary =
protocol family, not brand: the Icom core keeps its verified behaviour, and
Xiegu-specific semantics live where they can be read next to their provenance.

**D2 — CI-V address discovery instead of a constant.**
Xiegu publishes no G7250 address. `connect()` walks `0xA4` (X6100/X6200, and
IC-705's address — which is why wfview's 705 rig works on those radios) →
`0x88` (stock G90/G106) → `0x70` (legacy G90), and keeps the first one that
answers a frequency read. `MRRC_G7250_CIV_ADDR` pins one candidate when the
probe picks wrong. Rejected alternative: shipping one address — a wrong one
produces "connected, silent, no explanation", the failure mode the FT-891 baud
ladder was added to kill.

**D3 — no CI-V `0x27` scope; the spectrum comes from the LAN IQ stream.**
The X6100/X6200 have no CI-V scope and nothing suggests the G7250 does. So
`init_scope()` is inert, `set_scope_*` return `False`, `scope_on` leaves the
poll table (each poll would otherwise spend a NAK every 2 s), and
`create_scope_producer()` returns a `G7250LanIQProducer` **only** when
`MRRC_G7250_LAN_IP` is set. Without an address the model behaves exactly like
the Yaesu ASCII-CAT family: `scope_type="none"`, synthetic S-meter waterfall —
it still tunes and receives.

**D4 — one span, advertised through capabilities.**
The IQ window is fixed at ±24 kHz, so the profile/capabilities carry exactly
one span entry `{0: 24000}`. The frontend already rebuilds its span table from
`capabilities.scope_spans` (`static/ft710_ui.js:_rebuildCapSpanTable`), so no
JS change and no hardcoded 24 kHz anywhere.

**D5 — tuning writes both links.**
`set_frequency()` sends the CI-V command *and* the LAN tune frame: the IQ
centre only moves on the latter, so a CAT-only write would leave the waterfall
showing the previous centre line (the failure looks like "the waterfall is
offset by a few kHz and slowly gets worse").

**D6 — transmit stays gated.**
`verified=False` → `tx_gated=True` → keying refused until
`MRRC_ALLOW_UNVERIFIED_TX=1` (AD-019/NFR-067), releases never blocked
(Chapter 15 layering). A shipped box profile (`packaging/common/profiles/
g7250.env`) states `MRRC_ALLOW_UNVERIFIED_TX=0` explicitly, because a default
is not a decision.

**D7 — an empty Transceive item means "send nothing".**
`transceive_item=b""` and a one-line guard in `CivController.connect()`: the
X6100/X6200 did not publish a `1A 05 <item>` value either, and a guessed
payload can set an *unrelated* parameter. The backend polls instead of relying
on transceive broadcasts.

## 3. What is verified, and what is not

Verified **offline** (tests, `tests/test_xiegu_g7250.py`, 21 cases): registry
and profile wiring, capability gating both ways, the address probe (second
candidate wins / none answers / pinned), the tune frame **byte-for-byte**
against the published capture (`aa5555aa00010000000000d6c090` = 14.074 MHz),
IQ decode of truncated payloads, FFT peak position on a synthetic +5 kHz
carrier, `ScopeHandler` field contract, and a real UDP loopback.

**Not verified (needs a radio):** the CI-V address, whether the radio NAKs any
of the polled commands, meter curves (IC-7300 tables rescaled — same 100 W
class), ATU/TUNE form (`1C 01 02`), USB audio device name, IQ little-endian
assumption and I/Q sense (`MRRC_G7250_SWAP_IQ` covers mirroring), and whether
the radio keeps streaming IQ during TX.

First hardware session: `_diag_civ.py` (identity → read-only probes → static
meters → optional 200 ms TX) already drives the production `CivController`;
what is still missing is a Xiegu-specific wrapper that records the LAN side
(tune-frame echo, packet rate, ±24 kHz span) — tracked as follow-up work, not
claimed here.
