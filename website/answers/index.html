known-20261004-tls 已定位，待修复 网络 · 2026-10-04

接入云端报 CERTIFICATE_VERIFY_FAILED（诊断包也上传不了、软件更新检查失败）

macOS 打包版（v1.25.0 及更早）没有可用的 CA 信任库：应用里所有外发 HTTPS 都无法校验

诊断

  • 报错形如 certificate verify failed: unable to get local issuer certificate (_ssl.c:1032)，这不是 portal 或网络的问题——同一台机器上 curl 访问 portal 是 200、证书链完整
  • 根因：安装包把构建机的 OpenSSL 一起带走了，它的默认 CA 路径是构建机的 /opt/local/...（MacPorts），用户机上没有这个目录，于是信任库为空；空信任库同样导致诊断包上传失败
  • Windows 与源码运行不受影响（Windows 用系统证书库）

你要做的

  • 升级到 v1.25.1 即不再发生（随包 CA + 显式信任库；构建闸门会故意把信任库打空再要求真握手）
  • 还在旧版本上：在配置文件里加一行 SSL_CERT_FILE=/etc/ssl/cert.pem，然后重启 MRRC Modern
  • macOS 配置文件位置：~/Library/Application Support/MRRC-Modern/mrrc_modern.env
  • 重启后：接入云端、诊断包上传、软件更新检查应同时恢复
原始证据
  • Support bundle upload failed: <urlopen error [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate (_ssl.c:1032)>
  • libcrypto.3.dylib 编译期默认 CA：/opt/local/libexec/openssl3/etc/openssl/cert.pem

相关代码：net_tls.py（信任库）+ packaging/*/build.*（随包 vendor/ca/cacert.pem）

known-20261004-ftdi 已定位，待修复 产品缺陷 · 2026-10-04

频谱显示不对：一直是一条光滑的假曲线，看不到真实信号

macOS 打包版 v1.25.0（及 v1.18.0 起的同类构建）真频谱从未启动，界面画的是 S 表合成曲线

诊断

  • 日志特征：反复 scope_pipe exited (frames=0, connected=False) 与 Spectrum broadcast active: S-meter fallback；真频谱成功时应有 scope_pipe: first frame received — spectrum active
  • 硬件、驱动、库都没问题（FT4222 在 USB 总线上、两个 dylib 在包内，手工用正确目录运行立刻出帧）

你要做的

  • 升级到 v1.25.1 即不再发生（启动器改为经 _internal 解析相对路径，并补了签名包目录结构的回归测试）
  • 还在旧版本上：把配置里的 MRRC_FTDI_LIB_DIR 改成绝对路径 /Applications/MRRC-Modern.app/Contents/Resources/vendor/ftdi/macos，然后重启应用
  • 重启后刷新页面：频谱应变成真实底噪 + 信号（可在日志确认 first frame received — spectrum active）

  • 2026-10-04 07:01:10 [INFO] mrrc: Spectrum broadcast active: S-meter fallback, 1701 bytes/frame, 1 clients

发射功率小/没有？ 你看看

同一条根因的 SSB 版本：电台在发射，但实测 `ALC=0`、`Po≈0`，而服务端同时在把音频写进电台 USB 声卡 —— SSB 没有调制就没有射频功率；先查电台 `MOD Input`（`DATA OFF MOD` / `DATA MOD` = `USB`）

诊断

  • 「功率没有」在 SSB 下正是「没有调制」：`TX meters active: RF_PWR=56W | COMP=0 ALC=0 PWR=0 SWR=0` —— `RF_PWR=56W` 是功率设置值，`ALC` / `PWR` 才是实测。本段日志三次实测（18:05 / 20:17 / 20:46）全部 ALC=0，即调制器没有输入
  • 同时服务端在正常送音频：本段日志里连服务端自带的 CQ 录音也完整播完（`CQ: keyed the radio` → `CQ session: written=307 write_err=0 queue_drops=0 mic_drops=0`，6.1 s 全帧），浏览器麦克风一路也有大幅值（`peak=100%`），所以不是「没送出音频」
  • Icom 的调制输入源由 `SET` → `Connectors` → `MOD Input` 决定：`DATA OFF MOD` 管非 DATA 模式（SSB / AM / FM 语音），不含 `USB` 时语音发射只有载波 —— FM 表现为死载波、SSB 表现为没有功率，与同批另一份报告（对方听到发射但没声音）同源
  • 另外本次语音峰值起伏很大（`peak=1%/5%` 与 `peak=100%` 交替），手机麦克风的距离/增益也要一起调整；调制打开后 ALC 应稳定有读数但不进红区
  • 次要观察：`queue_drops` 多次出现（10~226），这台 Windows 机器的声卡输出节拍偏慢；若调制打开后仍有断字，见最后一条

你要做的

  • 电台菜单 `SET` → `Connectors` → `MOD Input`：`DATA OFF MOD` = `USB`（语音模式用；想同时保留手咪就选 `MIC, USB`）、`DATA MOD` = `USB`（数据模式）、`USB MOD Level` ≈ 50（不要 0）。
  • 同一组里 `USB SEND` 保持 `OFF`（IC-7300MK2 另见 `USB Keying (CW/RTTY)`）：它把 USB 口的 DTR/RTS 当作 PTT，设成 `USB(A) DTR/RTS` 后电脑一打开串口就等于按下 PTT。
  • 改完按住 PTT 说话：网页面板上的 ALC 表必须动 —— 不动就是调制还是没进来；再用第二台接收机确认能听到语音。
  • 麦克风电平：离嘴 5~10 cm 正常说话，避免长期 `peak=100%`（削波）或 1%（几乎无声）—— 本次两种极值都出现过
  • 若仍有断字/断续：把 `MRRC_AUDIO_TX_DEVICE` 锁定为启动日志里 `default=48000Hz` 的 WASAPI 条目，或换 USB 口 / USB 线（本次 `queue_drops` 最高 226）
