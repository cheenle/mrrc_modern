known-20261016-win-cert 已定位，待修复 网络 · 2026-10-16

Windows 上接入云端报 certificate has expired（浏览器却打得开门户）

不是门户、也不是网络：这台机器的证书库里有一份与被服务链条同名同密钥、却已过期的证书，应用（Python/OpenSSL）只认本机证书库，于是把库里那张放进链里判它过期；浏览器用自己那套根与链构建，所以同一台机器、同一条链，浏览器照常能开

诊断

  • 报错原文形如 certificate verify failed: certificate has expired (_ssl.c:1000)。这句话本身就说明 DNS/TCP/握手都通了 —— 是应用拿到证书之后自己拒绝的，不是门户没应答；门户侧同时刻实测证书链完整、有效期到 2026-12-29，且日志里没有来自该实例的任何请求。
  • 行号 _ssl.c:1000 是 Python 版本指纹：3.11=1016（盒子）、3.12=1000（Windows 安装包）、3.13=1032（macOS 安装包）—— 据此可确认失败的是 Windows 安装版。
  • 机制：Windows 会把见过的中间证书缓存进本机 CA 存储（Let's Encrypt 的中间证书会换代重签，缓存那份到期后正是这个形态）。OpenSSL 会把库里那份过期证书放进链里并判 expired，而且不会回退到服务器送来的那张有效证书（2026-10-16 在构建 VM 上用同一份 openssl 逐条复现）。
  • 浏览器（Chrome/Edge）用自己那套根与链构建，不吃本机 CA 缓存，所以表现为「浏览器能上、应用不能」。
  • 应用这一层属产品缺陷：net_tls.py 只在本机库为空时才启用随包 CA，也就是把「库非空」当成了「库可用」；**已修** —— 现在只信随包的根证书，不再采信本机证书库（随下一个版本到达用户）。

你要做的

  • 下载证书体检工具并**整个解压**后双击运行（默认只读体检，不改任何东西）：https://www.vlsc.net/mrrc_modern/downloads/MRRC-CertDoctor.zip
  • 它会用本机证书库对「门户下发的那条链」复现应用的判定，指出是哪一张证书、在哪个库里；确认后运行 MRRC-CertDoctor.cmd -Fix：把能证明是它的过期证书备份后删掉，必要时再问你是否导入当前的两张 Let's Encrypt 根证书。
  • 修好后：从托盘退出 MRRC Modern，再启动它，然后 ☰ -> 接入云端 (Cloud Hub) -> 呼号 + 运维给的一次性口令 -> 申请入口/接入。
  • 工具修不好时：桌面会留下 MRRC-CertDoctor-<时间>.zip，把它发给我们。注意诊断包上传与软件更新检查走的是同一条 HTTPS 路径，会一起坏 —— 属同一个原因。
原始证据
  • portal did not answer (https://portal.mrrc.vlsc.net): cannot reach the portal (URLError: <urlopen error [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: certificate has expired (_ssl.c:1000)>)
  • 同一台机器的 Edge 在 10:13 打开实例入口成功（nginx 记录 Windows NT 10.0 / Edg/155）：浏览器侧完全正常，只有应用那条 Python/OpenSSL 路径失败
  • 门户日志（2026-10-16）里没有该实例的任何 /claim、/status、/enroll —— 请求从未到达门户

相关代码：net_tls.py（不要把自己的信任判定外包给本机证书库）+ tools/windows/MRRC-CertDoctor.ps1（用户侧体检与修复）

  • **电台自己报的频率没动**：`18:38:20,850 IF poll: vfo_a=14270000 Hz (+0 Hz)`，同一分钟里台账的 `vfo_b_freq` 在 7.06 MHz / 21.4 MHz 之间来回跳 ⇒ 状态与电台显示分叉，就是用户说的「跳回原来频段」。
  • **代码缺口**：FTX-1 是真双收，`FA`/`FB` 分别主/副频率，`VS` 选操作侧、`FT` 选发射 VFO（`docs/ftx1-technical-analysis.md` §五）；而 `backends/yaesu/cat_core.py:set_frequency()` 只发 `FA`/`FB`（第 467–480 行），从不发 `VS`/`FT`；server 的 vfo_b 分支只 `radio.update(vfo_b_freq=freq)`（2551–2553、2946–2950），也不切换 active_vfo。按 PTT 才「切过去」与此吻合——PTT 走的是发射路径（FT），不是频率写成功。
  • **客户端把频率写到域下限**：日志里出现 `30000`、`38056`、`51475`、`41560`、`51389`、`142597`、`131187`（Hz）。30 kHz 在 FTX-1 的 `FA`/`FB` 合法域内（手册 30000–470000000，`ftx1-technical-analysis.md:325`），所以电台照收不误；服务端的 plausibility 下限也正好是 30000（`server.py:1258-1260`），拦不住 ⇒ APP 侧存在单位/取值错误，一次「切频段」就把频率送进荒区，随后被轮询纠回。

  • 先在**网页端**验证归位：把当前 VFO 切换回 A（界面上的 A/B 键），再做频段切换与记忆信道调用。A 通道是 FP12 已修好的路径，若 A 正常、B 仍「跳回」，即可确认问题只在副通道。
  • 工作期间**不要用 APP 切频段**，只用网页端——日志显示 APP 会下发 30000 / 51389 Hz 这类值（30 kHz），电台接受但显示上等于换了个荒区，随后轮询又把你拉回去。

FTX-1升级到1.28.17的问题

1.28.17 升级本身没有失败：发射不成是盒子侧 USB 音频/CAT 同时掉线（换线/换口即可），频谱跨度报错是 FTX-1 后端缺 `set_scope_span` 的代码缺口，FT8 起不来是 venv 里 numpy/scipy 装坏了。

诊断

  • TX 失败的现场是「没有输出声卡」，不是后端/模型问题：`No audio output device found for TX` 紧跟 `PTT: TX audio stream failed — unkeying radio`，`_find_tx_device()` 只有在当前 PortAudio 设备表里连一个带输出通道的设备都找不到时才返回 None（`audio_handler.py:832`）。
  • 同一时刻 FTX-1 的 CAT 口也在消失：`Serial write error for 'FA': (5, 'Input/output error')` → `CAT port [已隐去] is gone (No such file…)`，18:25:06 起反复 gone / 18:26:13 restored。CAT 与 USB 声卡走同一根 USB，声卡从设备表里消失与该现象一致（USB 掉线/重枚举，多见于线材、hub 或供电不足）。
  • 音频恢复路径本版只成功了一半：`RX open failed ([Errno -9993] Illegal combination of I/O devices) — re-initializing PortAudio`（17:59:43）之后 18:24:37 记录 `RX audio restart failed — capture stays down`；恢复逻辑存在（`audio_handler._reinit_pyaudio`，先关两条活流再重建），但设备不在时无法恢复。
  • env.json 佐证：`audio.devices.rx/tx` 均为空、`configured_rx/tx = "USB Audio Device: - (hw:1,0)"`，`tx_stats.written=14 / queue_drops=16`；前一日 11:00 的日志里同一设备是健康枚举的（`[0] USB Audio Device: - (hw:1,0) (host=ALSA, in=2, out=2)`），说明是运行期掉设备而非升级后不认设备。
  • 频谱跨度报错是真实代码缺口：`Command error (scope_span=4): 'YaesuCatController' object has no attribute 'set_scope_span'` 反复出现。`server.py:_handle_ws_message` 的 `scope_span` 分支无条件 `await cat.set_scope_span(v)`，而 `backends/yaesu/backend.py:_make_delegate` 把基类抽象方法一律转发到 `_cat`，`YaesuCatController` 里没有该方法（`backends/yaesu/` 全无 `set_scope_span`），所以每次点跨度/回放设置就抛 AttributeError。FTX-1 的 profile 是 `scope_type="none"` / `scope_spans={}`（`backends/yaesu/backend.py:67-68`），本不该收到这条命令。
  • 频谱本身属预期：`Spectrum broadcast active: S-meter fallback, 1701 bytes/frame`——FTX-1 无 CAT 波形源（scope_type=none），由 S 表合成，不是缺陷。
  • FT8 不可用是 venv 损坏，非升级回归：`FT8 composition failed — running SSB-only`，随后 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0x80 in position 0`，栈点是 `numpy/random/_pickle.py → from .mtrand import RandomState`（scipy→numpy 二进制与 Python 3.11 不匹配/文件损坏）。历史检索（`CHANGELOG.md`、`SDD/14-version-history.md` 的 `scope_span` / 无输出声卡签名）无同签名记录，不能判为已知缺陷回归。

你要做的
