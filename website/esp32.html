一台拿在手上的操作终端

旋钮调谐、2.4 寸瀑布、耳机听音、按键发射。全部用现成模块拼，不打 PCB。这一页把硬件清单、接线、音频管线、PTT 安全链和带宽账摊开，最后是八个我还没想明白的问题——欢迎直接在评论区、群里或 GitHub issue 上反驳。

1. 先说三句结论

一、这不是重写一个客户端，是把现有协议换一种形态接一次。控制面、频谱、音频、PTT 四条通道服务端全都有，固件要做的是"按契约说话"。

二、唯一可能动服务端的地方是声音的码率。其余零改动——包括语音上行，服务端原生就吃裸 PCM。

三、真正难的不是网络，是硬件。ES8311 的时钟、EC11 的抖动、天线被手挡住，这三件事比写 MQTT 客户端更花时间。

2. 它做什么，不做什么

要做 走哪条通道
频率 / 模式 / 滤波 / 记忆信道 / AF 音量 /WSradio 控制面（JSON）
真频谱瀑布 /WSspectrum，连上先声明降档
RX 听音（耳机） /WSaudioRX，Opus 48 kHz 单声道
TX 语音（内置麦克风） /WSaudioTX，Opus 48 kHz 单声道
PTT（含完整安全释放链） /WSradio 的 ptt + txhb

明确不做：录音、CQ 一键呼叫、ATR1000 天调、FT8 操作、SDR 接收页。这些都是桌面端能力，手持终端不该背它们。

3. 硬件：全模块化，不打 PCB

用一块 5×7 cm 洞洞板做母板，模块插上去、关键线焊死。别用杜邦线拼整机——手持设备上，线会在第三次通联时某处松掉，然后你花两天查一个"音频偶尔断"的"软件 bug"。

3.1 引脚分配（已避开 S3 的雷区）

N16R8 是 octal PSRAM：GPIO 26-32 归 flash、33-37 归 PSRAM，内部硬连线，外部完全不可用。strap 脚 0/3/45/46、USB 19/20、UART0 43/44 也一并避开。

功能 GPIO 说明
SPI2 → 屏 SCLK 12 / MOSI 11 / CS 10 / DC 9 / RST 8 / BL 7 BL 走 LEDC PWM 调光
I2S0 → ES8311 MCLK 4 / BCLK 5 / LRCK 6 / DIN 16 / DOUT 15 单路全双工，MCLK = 12.288 MHz
I2C → ES8311 控制 SDA 1 / SCL 2 地址 0x18（ADDR 接地）
EC11 编码器 A 38 / B 39 / 按压 40 38-42 默认是 JTAG，用作 GPIO 后失去 JTAG
按键 PTT 41 / MODE 42 / BAND 47 / BACK 48 每个键独立上拉 + 100 nF

3.2 电源

LiPo 3.7V ── TP4056(充+保护) ──┬── SS12D00 ── MT3608(升 5V) ── DevKitC 5V 脚
                               │                                 └ 板载 LDO ── 3V3 ── 屏 / ES8311 / 上拉
                               └── 电池 JST

走 DevKitC 的 5 V 脚、由板载 AMS1117 出 3.3 V，是零风险路径。不要把外部 3.3 V 灌进 3V3 脚——那是 LDO 的输出端，反灌会打架。代价是约 0.7 W 发热。

电流预算：Wi-Fi 峰值 350 mA + 屏 60 mA + ES8311 30 mA ≈ 440 mA @3.3 V，2500 mAh 约 RX 9-10 h / 持续 TX 4-5 h。

3.3 七个会咬人的点

  1. GPIO 33-37 绝对不能用。网上大量 ST7789 教程用 GPIO 37 做 RST，在这块板子上必然点不亮，现象是"背光亮、无内容"。
  2. EC11 必须硬件去抖（A/B 各 100 nF 到地）。纯软件去抖在快速旋转时丢步，"转十格只跳七格"就是它。
  3. PTT 键独立上拉 + 100 nF。这是能烧功放的键，一次误触就是一次空载发射。
  4. ES8311 的 MCLK 必须给（12.288 MHz）。省掉 MCLK 的模块，音质与采样稳定性都会掉。
  5. ES8311 的 I2C 地址由 ADDR 脚决定：接地 0x18，接 3.3 V 0x19。模块上有跳线，先量再焊。
  6. 屏的 BL 一定要接。夜里 100% 亮度刺眼，PWM 调光是必需项。
  7. 板载 PCB 天线被手挡住会掉包。手持形态下这是真实问题，优先选带 IPEX 座的模块 + 小天线贴在外壳内侧。

4. 音频：两条管线，六个数字

4.1 下行（RX）

/WSaudioRX 帧 = [0x01][Opus 包]
  → opus_decode(48 kHz mono, 20 ms, 960 samples)
  → 抖动缓冲（目标 200 ms，弱网可调到 400 ms）
  → I2S0 TX → ES8311 → 耳机

丢包用 Opus PLC（opus_decode(NULL) 外推 120 ms），不要填静音——听感上静音比 PLC 更糟。

4.2 上行（TX），分两个台阶

台阶 A（阶段 4）：裸 PCM。服务端原生支持 0x00 帧，固件只需在 48 kHz Int16 块前加一个字节。零编码器风险，先把"能说话"跑通。 

ES8311 ADC (48 kHz / 16 bit) → 960 样本/20 ms → [0x00] + 1920 B → /WSaudioTX

台阶 B（阶段 6）：Opus。用官方组件 esp_audio_codec（位率 20-510 kbps，支持 48 kHz 单声道、FEC、DTX、VBR），取 20 kbps + 20 ms + VOIP 模式。 

ES8311 ADC → 20 ms 帧 → Opus 编码 (48 kHz mono, 20 kbps) → [0x01] + 包 → /WSaudioTX

4.3 带宽账（这是"必须上 Opus"的全部理由）

路径 编码 码率 每分钟 每小时
RX 下行（现状） Opus 48k 64 kbps 0.48 MB 28.8 MB
RX 下行（降档后） Opus 48k 24 kbps 0.18 MB 10.8 MB
TX 台阶 A PCM 48k/16b 768 kbps 5.8 MB 345 MB
TX 台阶 B Opus 48k 20 kbps 0.15 MB 9 MB

差 38 倍：每天通联 30 分钟，裸 PCM 是 5 GB/月，Opus 是 108 MB/月。所以台阶 A 只用于局域网验证，不上公网。

5. PTT：能发射，就得能收回来

PTT 是这个项目里唯一"写错会烧东西"的部分。服务端已经有三层保护（键控会话断开强制 RX、活性闸门、发射时长上限），固件这一侧补三条： 

IDLE ──按下──► KEYING    : ptt:true → 100 ms 后 txhb → 每 1.5 s txhb → 开始推音频
KEYING ──松开──► RELEASING : 停推帧 → 发 "s:" → ptt:false → 200 ms → IDLE
KEYING ──180 s──► FAILSAFE : ptt:false，锁止到完全松开再按
KEYING ──心跳连续 2 次失败──► FAILSAFE : ptt:false → 触发重连
  1. 任何退出路径先发 ptt:false，包括异常、看门狗复位、重连之前。
  2. 只有 tx_status == 1 才推麦克风帧，避免未键控时把音频灌进服务端队列。
  3. 服务端的拒绝要显示出来：FT8 引擎正在发射（约 13 秒）、CQ 呼叫进行中，这两种情况服务端会回 error 并拒绝键控，固件必须提示并回到 IDLE，不能停在"我以为在发射"。

心跳为什么是 1.5 秒？Cloud Hub 的实例统一把 MRRC_REMOTE_SESSION_TX_HEARTBEAT_S 设为 5 秒，检测粒度 0.25 秒。客户端按 1/3 取周期，弱网抖动才不会随随便便把载波打断。另外，txhb 是"能力声明"——发过一次，这条会话就永久受闸门监控，直到超时或断连。

6. 六个阶段，每段单独可验

阶段 1控制面登录 + 旋钮调谐 + 频率/模式显示。验收：转旋钮，电台跟着变。
阶段 2频谱/WSspectrum + 瀑布 + S 表。验收：与浏览器同观，形状一致。
阶段 3RX 听音Opus 解码 + 抖动缓冲 + 耳机。验收：连听 30 分钟不断续。
阶段 4TX + PTT裸 PCM 上行 + 完整状态机。验收：对方能收到；松手立刻停。
阶段 5公网TLS + 前缀路径 + 重连。验收：4G 热点连回家里的电台。
阶段 6Opus 上行20 kbps 编码 + 服务端 RX 降 24k。验收：一小时通联 < 20 MB。

这样安排的好处是：任何一步出问题，你知道问题在哪一层。不会出现"全写完才发现声音不对"。

7. 八个我还没想明白的问题

下面每一条都给了我的倾向和理由。反对意见比赞同更有用——如果你觉得哪条错了，直接说错在哪。

Q1RX 码率怎么降？
  • ① 全局加一个 MRRC_RX_OPUS_BITRATE，默认 64000，降到 24000（一行改动）
  • ② 按客户端协商一个 audioCaps，对标现有的 spectrumCaps（改动较大）

倾向 ①：语音 24 kbps 对浏览器听众几乎无损，② 留到真有人抱怨再说。

Q2TX 用固定 20 kbps 还是 VBR？

固定码率稳，抖动小；VBR 省流量但局域网/4G 上的突发不好预测。还有 DTX（静默不传），能省掉一半下行。

倾向：固定 20 kbps + DTX。不确定的是 DTX 会不会让服务端的抖动缓冲出问题。

Q3频谱取哪一档？

mid（divider 2，30→15 Hz）还是 low（divider 4，30→7.5 Hz）。850 bins 不变，只是刷新率。

倾向 mid：屏只有 320 px 宽，850 bins 本来就要降采样，7.5 Hz 的 waterfall 看着会滞。

Q4Wi-Fi 凭据怎么配？
  • ① SmartConfig（手机 App 广播 SSID/密码）
  • ② 开软 AP + 网页表单（和盒子的 /settings 同款体验）
  • ③ 编译期写死（只适合自己用）

倾向 ②：经验上和盒子的配网体验一致，老人也能跟着做。代价是要多写一个 AP 模式的网页。

Q5电池多大？

2500 mAh 偏重（约 50 g），TX 约 4-5 小时；1500 mAh 轻 25 g，TX 只剩 2.5-3 小时。

倾向 2500。手持设备最怕的是"中午没电"，重 25 g 反而不容易察觉。

Q6和浏览器同时在线，会互相打断吗？

读代码确认不会：服务端在 PTT key-up 时按 token 重新分配上行所有权（_claim_tx_owner_for_token），谁按键谁拿到麦克风。ESP32 常开 /WSaudioTX 是安全的，前提是四条 WS 共用同一个 token。

倾向：不需要额外优先级规则。但这条只是代码分析，没有真机验证过，属于"待实测"。

Q7旋钮要不要段落感？

EC11 有段落 vs 光学编码器（无档位、可快转）。电台调谐是肌肉记忆动作，很多人依赖"咔哒"的档位。

倾向 EC11 有段落。但如果你常做 SSB 快速扫频，无段落可能更顺手——这一条纯属手感，得摸过才知道。

Q8要不要显示 FT8 解码结果（只读）？

FT8 的消息在 /WSradio 之外，需要额外订阅。手持终端上显示呼号列表确实有用（野外追传播时能一眼看到谁在喊），但会增加一条通道和一块 UI。

倾向：第一版不做。等基础四通道稳定了再说。

8. 怎么参与

这一页是设计草案，不是文档。真正开工前，最需要的是反对意见和实测数据：

  • 觉得某个器件选型不对（更便宜的、更好买的、更省电的），直接说型号；
  • 做过 ESP32 + ES8311 / I2S 全双工的，说说你踩的坑；
  • 对 PTT 安全链有异议，尤其是"心跳周期 1.5 s"和"180 s 上限"这两个数；
  • 怀疑某条协议结论（页面上引用的行号都在仓库里），欢迎直接去对代码。
