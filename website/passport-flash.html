Plug it in: the box flashes the Passport, config and all

A terminal straight from the factory knows nothing. It has no Wi-Fi, it does not know where the box is, and it does not know the box's password. The old flow: join the hotspot it raises (iOS calls it "no internet"), then type the Wi-Fi name, the Wi-Fi password, the box address and the box password on a phone keypad. The box already knows all of it.

Three steps now

  1. Unplug the radio and plug the Passport into the box's USB port.
  2. Open https://<box>:8888/passport in a browser.
  3. Pick a firmware, pick the device, fill in four fields, press Start.

Unplug it afterwards and power it from any USB supply — it joins the Wi-Fi by itself and shows up on the box as a terminal session.

The four cards on the page

1 · Firmware

Press Read catalog once; the box fetches the list of flashable builds from this site. Pick one and press Download and verify. The image is downloaded and its SHA-256 checked before the flash starts, so the write phase contains no download and a failure leaves no half-image behind.

2 · Device

Only ESP32-class serial ports are listed, and the radio's own port is never a candidate — not just that one path: the whole USB device. The FT-710's CP2105 exposes CAT and scope as two ttys from one chip, so excluding one path is not excluding the radio. If the board does not appear, hold its BOOT button while plugging the USB cable in, then press Re-detect.

3 · The configuration to write

Field Prefill
Wi-Fi SSID the network the box is on (editable)
Wi-Fi password empty — typed once per board; the system does not hand a passphrase to a web page
Server address this box's LAN address (change it to the public entry for away-from-home use)
Box password empty = use this box's own; the value never appears in a response and never reaches a log

4 · Write

The log pane shows esptool's own output. The job is a single-slot lock: a second press while it runs answers 409. The state pill ends at done or failed with a reason.

What it writes, and why it cannot report a false success

Step Meaning
chip id identify the chip; a board that is not an ESP32-C3 is refused before the first write
firmware 1.3.2 the merged image at 0x0 (bootloader + partition table + app), with --verify
wifi config the NVS partition at 0x9000, with --verify
read back read 0x9000 back and compare it, field by field, with the intended config
reset hard reset; the board boots with its new configuration

The NVS encoding is byte-for-byte identical to ESP-IDF's own esp-idf-nvs-partition-gen, and a test pins that down. A wrong format throws nothing — the device silently falls back to compile-time defaults, which means the Wi-Fi you just wrote quietly disappears. Byte equality is the only evidence worth trusting.

What firmware 1.3.2 changes

  • The waterfall no longer stays demoted after a transmission. The old code restored "the tier in effect" on unkey — but key-up had just overwritten that with the cheap tier. Every transmission left the link on the cheapest one until the health watcher promoted it two minutes later. Field log: PTT at 12:32:55, still low at 12:36:26. The tier is two variables now — what the link was judged able to carry, and what is in effect — and unkey restores the former.
  • A 3 s hold on UP reopens the setup hotspot. Previously only a board with no configuration at all could reach the setup page; a wrong Wi-Fi or a different box meant erasing flash. The hold arms a one-shot flag and reboots; the next boot enters setup before station mode claims the radio, so the heap is still free.

Three boundaries

  • No passphrase in the page, none in the log. The Wi-Fi passphrase only enters the in-memory NVS image; every line that reaches the page or server.log is scrubbed (the log pane ends up in screenshots and support bundles). When the box-password field is left empty the server substitutes its own value, which never travels over HTTP.
  • The radio is never a candidate. Writing 1.7 MB into an FT-710's CAT port is not a failed flash, it is an incident.
  • A wrong chip aborts before the first write, so a mis-plugged board is never half-flashed; and a read-back mismatch fails the job on purpose — a short read-back is not a trimmed success.

Requirements and troubleshooting

This needs box 1.29.0 or newer. The flasher travels with the code (vendor/esptool/), so there is no pip, no network and no restart involved — a patch that moves files is enough.

Symptom What to do
Start is greyed out, "no esptool on this box" the tree is old or incomplete: update the box, or install esptool once
"that port is not in the list" it disappeared between listing and starting, or it is the radio's. Press Re-detect
"a flash is already running" one at a time. Wait for it, or reload the page afterwards
catalog: … / download: … the box cannot reach this site, or the image SHA does not match. Check its network and retry
Flashed fine but the board never connects almost always a wrong Wi-Fi passphrase or address. Re-run card 3 with the same firmware; the NVS write is fast
Full steps, an acceptance checklist and the troubleshooting table are in the operator guide. The terminal's own story is the essay on keeping a call alive on a train.
