MRRC Terminal SDD — Software Design Description

ESP32-C3 handheld terminal: receive, transmit, display and provisioning IBM Team Solution Design (TeamSD) aligned, with one local amendment (chapter 00)

Purpose

This SDD is the design record for the firmware in this repository. It exists because the same fault was found twice, months apart, by two different people, from the same wrong hypothesis. The record’s job is not to describe the code — the code does that — but to keep three things attached to each other:

  • what the device must do, as numbers that can be measured (05);
  • why it is built this way, as decisions with their alternatives and costs (08);
  • what went wrong before, as evidence that cannot be quietly forgotten (15, and the incident tables in ../docs/transport-tuning.md and ../docs/optimization-notes.md until chapter 14 exists).

Every claim here was measured on this board or on the server that feeds it. Where a claim is not measured, the text says so and marks the chapter or row as proposed. Chapter 00 makes that rule load-bearing: it is the highest-priority chapter in this document and it governs how all the others may be written.

Writing an empty chapter would claim coverage this document does not have, which is the one thing chapter 00 §V5 forbids.

Boundary. This document owns the terminal: its codec, buffers, tasks, display, provisioning, and the device half of the transmit path. It does not own the server’s session policy, the radio’s CAT behaviour, or the network between them. Where a firmware decision depends on a server behaviour, the dependency is named in 08 and the server is cited as the owner.

Reading order

For a change to the audio or transmit path: 00 → 15 → 08 AD-002/AD-003/AD-004 → 05 §5.1/§5.3. For a change to display or memory: 00 → 05 §5.4 → 08 AD-001/AD-005 → docs/UI.md. For anything else: 00 first, always; it is shorter than the mistake it prevents.
