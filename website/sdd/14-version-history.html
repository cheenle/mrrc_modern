SDD V2.9 2026-07-26 Kimi Windows TX crackle fix — WASAPI 48 kHz output (Win11 KVM field report: transmitted audio “咔啦咔啦” noise instead of voice). Measured on the rig: the C-Media codec’s MME 44.1 kHz playback path paces ~1.4× slow (50×20 ms stream.write() block 1.36–1.42 s instead of 1.00 s at 44.1/48/32/16/8 kHz; only 22050 Hz paces 1.02), so the TX drain loop falls behind, the 400 ms queue cap drops 24–34 % of voice frames (TX session written/fed 330/432, 195/296 — macOS production shows 96–97 %), chopping transmitted audio into crackle. The codec’s WASAPI entry at its native 48 kHz mix rate paces correctly (0.96). Fix: start_tx() prefers the same-name WASAPI entry on Windows (_wasapi_tx_variant) and opens the stream at that entry’s native rate; feed_tx_audio passes 48 kHz PCM straight through at 48 kHz (no 48→44.1 resample) and pre-buffer/cap/graceful-drain budgets are computed from the actual stream rate (getattr fallbacks keep module constants for 44.1 kHz). macOS unchanged (CoreAudio device domain stays 44.1 kHz); RX capture stays MME 44.1 kHz on Windows (paces fine). v1.7.5 hotfix: the v1.7.4 branch referenced sys.platform without the module import (NameError on every PTT) — new end-to-end StartTxWindowsTests cover start_tx on both platforms. AD-011 amended: device-domain rate is host-API-dependent, not universally 44.1 kHz — this overrides the audio-pyaudio-rate warn rule with runtime evidence. 7 new tests (WindowsWasapiTxTests + StartTxWindowsTests); suite 409 tests. SDD V2.8 2026-07-26 Kimi Windows RX audio dies after first PTT (full-duplex wedge) + scope resync that actually works (Win11 KVM field report: audio perfect after server restart, gone after one PTT). RX root cause: on Windows (MME/DirectSound), opening the TX playback stream on the FT-710’s C-Media USB codec silently wedges the RX capture stream — it stays open and error-free but delivers silence; macOS CoreAudio is unaffected (hardware capture verified healthy, max 43% FS, with the server stopped). Fix: AudioHandler.restart_rx() reopens the capture stream on every TX→RX transition, hooked in _broadcast_state on tx_status dirty (covers PTT/TUNE/physical PTT/dead-man), Windows-only no-op elsewhere (macOS must not pay the reopen cost per PTT). Scope root cause: the byte-by-byte sync_stream resync (wfview port) could never succeed on the FT4222 — every 1-byte SingleRead is its own SPI transaction (CS toggles per call), making a contiguous multi-byte sync pattern unobservable; it only consumed the stream and churned recovery into fatal:too_many_reinits after every PTT (V2.7’s TX-pause resume path used it). Replaced with resync_device() (close → 1 s idle-bus settle → reopen — the pattern that empirically realigns, same as a pipe restart), used by both the TX→RX resume and the bad-frame path; MAX_SYNC_ATTEMPTS/sync_attempts_this_device removed. AD-008 amended (Windows full-duplex wedge + restart_rx). 4 new tests (RestartRxTests); suite 402 tests. Docs: AD-008, AGENTS.md module table, tests/README counts, CHANGELOG v1.7.3.

SDD V2.7 2026-07-26 Kimi TX-safe spectrum: scope_pipe TX pause + Windows process-tree kill (field log from the Win11 KVM test rig: after every PTT the waterfall showed fallback/garbage for 30–45 s). Root cause: the FT-710 garbles its scope stream during TX (normal radio behavior), but scope_pipe was TX-agnostic — it kept reading, tripped sync_lost → spi_stalled device re-init → more sync failures → fatal:too_many_reinits, then a server-side pipe restart before real FFT frames returned. Second defect surfaced by the same log: on Windows, killing the PyInstaller onefile bootloader (proc.terminate()) orphaned the real worker, which kept the FT4222 open, so the next pipe failed FT_OpenEx with FT_DEVICE_NOT_FOUND for ~10–15 s (matches the long-standing code comment). Fixes: (1) the pipe protocol gains a stdin control channel — the server pushes TX:1/TX:0 on every tx_status dirty broadcast (_notify_scope_pipe_tx, covers PTT/TUNE from any source, re-synced with force=True on pipe start); while TX is active the pipe pauses SPI reads and freezes all sync/stall/reinit counters (tx_pause STATUS), and on TX→RX runs one clean sync_stream re-sync (tx_resume:resync); (2) Windows pipe teardown uses taskkill /PID <pid> /T /F (_terminate_process_tree_sync, POSIX keeps SIGTERM), and the pipe treats stdin EOF (parent died) as a shutdown signal — a second orphan guard alongside the stdout-heartbeat EPIPE path. Frontend: waterfall/FFT canvases show “TX 发射中 — 频谱暂停” while tx_status != 0 instead of stale rows. AD-005 amended (stdin control channel + tree kill), §9.5.1 diagram updated, UC-004 flow unchanged from the client’s perspective. 13 new tests (test_scope_pipe_tx.py: control-line parsing, TX-notify transitions/force/dead-pipe guard, taskkill vs SIGTERM); suite 398 tests. Design Baseline Notes

  • Radio: Yaesu FT-710 superheterodyne transceiver (not an SDR).
  • CAT Protocol: Direct serial CAT via pyserial — no Hamlib, no rigctld, no TCI.
  • Scope: FTDI FT4222 SPI chip provides 850-point FFT data. Falls back to synthetic S-meter Gaussian spectrum when unavailable.
  • Audio: Bidirectional through FT-710’s built-in USB audio interface via PyAudio (44.1kHz native device rate). Opus codec (RX 64kbps, TX 64kbps CBR, both 48kHz) with Int16 PCM fallback. audio_resample.py bridges the 48kHz codec domain ↔︎ 44.1kHz device domain (960↔︎882 frame-aligned).
  • Auth: Shared-password session auth (ft710_auth cookie, 30-day, ?token= on WebSocket).
  • PTT Safety: Client-side PTT watchdog (500ms) + dead-man switch (WS disconnect) + pagehide handler + server-side TX status poll (0.5s). No TX0 verify loop on release (radio obeys TX0 fire-and-forget). TX audio drain=50ms. TUNE is press-and-hold.
  • Polling: 7-task adaptive scheduler: IF 0.1s (FA/MD0/SM0), VFO 0.5s (VS/FB), TX status 0.5s, TX meters 0.5s (RM3/4/5/6, TX only), settings 2s, slow 5s, connection watchdog 1s. Poll queries use 0.25s timeout and cooperate with priority-command preemption (_cancel_polls). Poll loops re-check skip state AFTER each in-flight query response and discard stale reads; filter sets are verified by a 150 ms SH0; read-back. After a successful watchdog reconnect the scheduler re-runs the scope-init CAT sequence (EX040101/EX040200) via its on_reconnected hook — a USB re-enumeration resets the radio’s scope output.
  • Meters: RM3-8 raw 0-255 values calibrated via piecewise-linear tables from FT-710.rig (Power/SWR/Vd/Id). Frontend displays watts, SWR ratio, volts, amps — not raw numbers.
