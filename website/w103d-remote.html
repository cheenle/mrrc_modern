W103D 盒子遥控器指南

一台盒子、一支蓝牙遥控器，人站着就能把电台调好、按下去就能说话。这份指南只说遥控器： 怎么配对、每个键干什么、不好用时先查哪一条。

1. 能用的遥控器

盒子认的是标准的蓝牙 HID 遥控器（就是能和手机、电视配对的这一类）。配好之后， 内核会多出一个叫 <遥控器名字> Keyboard 的输入设备，按键从这里进来。

已经实测通过的一支：中国移动的语音遥控器，蓝牙名 CMCC_Voice_Remote。

两件目前不行的事，先说明白，省得白折腾：

板子上没有焊接收头，对着盒子按键收不到任何波形。我们试过两支遥控器，/dev/lirc0 一直是空的。

蓝牙耳机那种音频协议，盒子读不出来。

  • 红外遥控器不行。 盒子在设备树里注册了红外接收器（meson-ir），但这一批
  • 遥控器自带的麦克风用不了。 它的语音走的是厂商自己的一条蓝牙通道，不是标准

2. 配对（只做一次）

前提（镜像已带）：服务账号 mrrc 要在 input 组里 —— /dev/input/eventN 是 root:input 0660。缺了它，遥控器配得再好，mrrc-localctl 每次打开都是 Permission denied，而界面上没有任何地方会说「缺组」。查：id mrrc 里有没有 input。

  1. 让遥控器进入配对模式：同时长按「OK + 返回」约 5 秒，指示灯开始快闪。
  2. 浏览器打开盒子的 /settings，找到「遥控器」，点「搜索附近的遥控器」（约 12 秒）。
  3. 列表里出现 CMCC_Voice_Remote 后点「配对」。

列表里有一堆东西时挑哪个。 排在第一行的那台就是它，两个标记一起看： 行尾写着 「遥控器/键盘」（bluez 认得出它是 HID 键盘，这条最硬）， 后面跟着信号强度（贴着盒子时 -40 ~ -60 dBm）。排列顺序是 「像遥控器的在前 → 当场扫到的在前（强的在前）→ 只有缓存名字的在后」，所以 遥控器在配对模式时必然在最上面。没有信号强度的那几行是 bluez 记得、但此刻没在广播的 设备（灯不闪了就是这样）。

配对为什么要这么久、为什么必须由浏览器点。 盒子上跑的是交互式 bluetoothctl （pty + --agent NoInputNoOutput）。这不是花活：一次性 bluetoothctl pair 不注册配对 agent，bluez 发出的 Pairing Request 里绑定位是 0，而 BLE HID 遥控器必须存一把密钥才能 重连，它会直接回 SMP Invalid parameters（0x0a）——链路建起来了，配对被一句话否掉。 进了 pty 之后请求变成 Bonding (0x29)，一次就成，bluez 随后建出 CMCC_Voice_Remote Keyboard。

只发现一台正在广播的遥控器时，页面会自己配对（不用再点「配对」）——扫描结束直接 开始配，配上就写「已配对，按键可用 ✓」。没配上时页面会把 bluez 的原话贴出来 （例如 Device … not available = 遥控器已经退出配对模式，AuthenticationFailed = 握手时它走了），照着那句话处理即可。

看到页面写 「已配对，按键可用 ✓」 就成了，按一下方向键验证。

配对失败最常见的原因是它没进配对模式，而页面/命令不会告诉你这一点。 遥控器只在按下「OK + 返回」后的那几十秒里可以被配上；一旦超时，bluez 仍然会把它的 名字留在设备列表里（那是缓存），此时点「配对」只会得到 Device … not available。 现在页面与 net_bt.pair() 的做法是：直接配，bluez 说不可用就隔 5 秒重试，最多 6 轮 （约三分钟）。不用"先等它广播"做前置判断——2026-10-19 实测，这台遥控器的广播里 没有 RSSI（scan on 只出 [NEW] Device … CMCC_Voice_Remote，别的设备才有 RSSI: 行），按 RSSI 判"在不在广播"会永远判成不在，操作员把键按烂也走不到配对。 重试把时序问题变成概率问题，而且失败时给出的是 bluez 的原话 + 该做什么。

没有网页的时候（命令行）

SSH 进盒子（root 或 mrrc）后：

bluetoothctl --timeout 20 scan bredr          # 遥控器是经典蓝牙
bluetoothctl --timeout 25 pair  <地址>
bluetoothctl trust <地址>
bluetoothctl info <地址> | grep -E "Paired|Bonded|Connected"

配好了但按键没反应？按这个顺序排

Paired: yes 不等于能用。判据只有一个：/proc/bus/input/devices 里出现 CMCC_Voice_Remote Keyboard，并且连续几秒都在（bluez 建了又拆时，单点采样会骗人）。 页面上的表现为「已配对，但按键没有响应」。

两个不同的病，救法不一样：

日志里的句子谁在说病救法
No attribute found within the given rangebluez 自己守护进程内存里的 GATT 数据库残缺。链路通着、密钥也在，但它拿这份坏库去读，读不到就拆设备（dmesg 里 …0300.0002 → …0300.0004 一路翻号）重启 bluetoothd：sudo systemctl restart bluetooth。磁盘上的 bond 原样重读，一次就成
unlikely error（ATT 0x0E）刷屏，且没有任何属性被读到遥控器链路没加密。它拒掉每一次属性读取清 bond → 控制器上下电 → 让遥控器重新进配对模式 → 再配

第二行的 0x0E 单独出现不足以判定没加密——2026-10-19 现场它在 GATT 残库的情况下也刷， 而 restart 之后同一把密钥就正常了。决定性的是 bluez 自己那句 No attribute found： 那句话出来就是残库，别去动 bond。

修复版 net_bt.pair() 已经按这个顺序做：配上但键盘设备不稳定 → 先通过 root helper 重启 bluetoothd（无破坏性，bond 不动）→ 仍然不行才清 bond 重配。

手动排障时两条都能直接敲：

sudo systemctl restart bluetooth              # 先试这条（最常见、最轻）
bluetoothctl remove 0C:F3:CE:B0:88:75          # 再试这条（真·密钥对不上时）
bluetoothctl power off ; sleep 2 ; bluetoothctl power on
# 遥控器重新进配对模式（取电池 10 秒，再按住 OK + 返回 5 秒），然后 pair 一次

那条 bluetoothctl power off/on 单独打不要用 remove 连着打：连接会话只能有一条。 两个会话同时连，bluez 会回 le-connection-abort-by-local（本地主动中止），而一次被中止的 服务发现会在内存里留下半份数据库——也就是上面第二行的病。

▲ / ▼频率加上/减去当前步进
◀ / ▶换步进档位（100 Hz / 1 k / 5 k / 10 k / 100 k）
频道 + / −逐个跳固定信道（下表），模式跟着一起换

发射有三重保护，和网页上一样：松手就停、遥控器掉线也停、单次发射有上限。

这条表就是 local_ctl.py 里的 PRESET_CHANNELS：改频点或模式只改那一处， 频率和模式是成对发的（先频率后模式，免得电台换波段时自己把模式改回去）。 注意它是遥控器专用：网页上调频率不受影响，也不会被你上次按到哪儿影响。

4. 直接输入频率

数字按 kHz 算，按「确定」生效。举例：

想去的频率按
7.050 MHz7 0 5 0 → 确定
14.070 MHz1 4 0 7 0 → 确定
3.573 MHz3 5 7 3 → 确定

按错了不要紧：按「返回」清掉，或者等 3 秒不管它，输入框自己作废。 输入途中按 ▲▼ 也会把没提交的数字丢掉，直接调频。

5. 出问题先查这几条

现象先看什么
按键完全没反应bluetoothctl info <地址> 是否 Paired: yes；journalctl -u bluetooth -n 40 里有没有 unlikely error（有就按 §2 重配）
只有部分键有用按键表按扫描码认键。这类遥控器上「设置」「M」「#」三个键的键码都是 240，只看键码会混成一个。换遥控器要改键位表，见 §6
按电源把盒子关了grep HandlePowerKey /etc/systemd/logind.conf 应该是 ignore；不是就改掉再 systemctl restart systemd-logind
遥控器连上又断，反复BLE 遥控器空闲时会自己断开、按键时再连，这是正常的；只要按键有效就不必管
Wi-Fi 偶尔卡一下这颗芯片的蓝牙和 Wi-Fi 共用一路 SDIO，遥控器连续操作时 Wi-Fi 可能短暂抖动，几秒内自愈
服务没在跑systemctl status mrrc-localctl，日志 journalctl -u mrrc-localctl

6. 换一支遥控器

按键和动作的对应关系在 local_ctl.py 的 DEFAULT_KEYMAP 里，一张 「扫描码 → 动作」的表。换遥控器的步骤：

扫描码（比如 value 70052），下一行是键码；

  1. 先认出它发什么：evtest /dev/input/eventN 里每个键有两行，MSC_SCAN 的值就是
  2. 在表里加一条，扫描码写成 "u:0x70052": "freq_up"；
  3. 不想改代码就写一份 JSON 覆盖文件，用环境变量指过去：
{ "u:0x70052": "freq_up", "u:0x70051": "freq_down" }
# /etc/systemd/system/mrrc-localctl.service 里加上
Environment=MRRC_LOCALCTL_KEYMAP=/opt/mrrc_modern/env/keymap.json

可用的动作名：ptt、freq_up、freq_down、step_up、step_down、band_up、 band_down、enter、cancel、menu、mode_next、vol_up、vol_down、 digit:0 … digit:9。

7. 它到底怎么连起来的

遥控器  ──蓝牙──>  盒子内核（HID 键盘）
                      │
                      ▼
              mrrc-localctl（读按键、查表）
                      │  本机 wss://127.0.0.1:8888/WSradio
                      ▼
                 电台服务（和网页发的是同一套命令）

这条链路只走本机回环，不经过局域网，也不经过云端。遥控器配在盒子上，就只对这台盒子有效。
