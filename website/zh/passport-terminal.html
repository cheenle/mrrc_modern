一块 ESP32-C3 手持终端
如何在高铁路线上保持通话

把 FoloToy AI Passport 改造成 MRRC Modern 的手持终端：240×320 屏、四档旋钮、 一条 TLS 连接同时承载控制、双向 PCM16 音频与频谱。本文讲的是"把卡顿干掉" 这件事——五个互相独立的原因，每一条都是测出来的，不是猜出来的——以及证明它们 的那些数字。

这东西是什么

Passport 是一块可穿戴设备：ESP32-C3、8 MB flash、没有 PSRAM。Wi-Fi、TLS、 240×40 瀑布、频谱曲线、音频通路与 UI 渲染全部挤在同一块 400 KB 的 SRAM 和 同一个 160 MHz 核心上。它连的是和 PC 相同的 MRRC Modern 服务端，所以有意思的 不是功能清单，而是让一颗三美元的 MCU 在这个预算里维持实时音频流。

卡顿是五个问题，不是一个

症状每次都一样——声音断续——而前三次修复都把它弄得更糟，因为每一次都 打在了错的层上。真正起效的做法是：在测量指出是哪一层短之前，什么都不改。

  • 是接收队列，不是带宽。设备只收到 31.3 KB/s 流里的 25.6–28.6 KB/s，而同 Wi-Fi 的对照客户端能收满。两次调大 TCP 窗口都毫无变化， 因为窗口从来没满：每连接的接收邮箱只有 6 个 pbuf、乱序队列 4 个、A-MPDU 块确认窗口 6。改成 8/8/16 之后，设备收满全部 49 KB/s。
  • 播放从空环开始。服务端并不是匀速 50 帧/秒：实测到达间隔 p95 67–74 ms、p99 230–299 ms。没有缓冲垫时，每个空隙都会饿死 I2S DMA， codec 就填静音——每秒 3–5 次环空唤醒。加 160 ms 预缓冲、干涸 200 ms 后重攒， 这项归零。
  • 服务端一直在等我们。它自己的计数 max pump stall 是 5791 ms——它等这个客户端读了将近六秒。队列修好之后：3 ms。
  • 上行跑在 Nagle 下。tcp_transport 和 esp_websocket_client 都不调用 setsockopt，于是每个 641 字节的 PCM 写入都在等上一段被确认。323 次发送里有 100 次阻塞超过 30 ms， 最坏 89 ms。打开 TCP_NODELAY 并把发送缓冲翻倍后：慢发送 0–3 次， 最坏 9–17 ms，服务端每次发射都报 queue_drops=0。
  • 一级只会制造削波的麦克风增益。发射音频峰值 100%、5% 的样本 被削。两级增益叠加：codec 的模拟 PGA +30 dB 与服务端软件增益 +12 dB。把服务端 降到 +3 dB 并没有帮助（5.0% → 5.8%），正是这个反证说明峰值在 ADC 就 已经顶满。0 dB 时峰值 40%，整次发射新增削波为 0。

然后是 UI 吃掉了 CPU

音频干净之后，taskLVGL 仍占 56–61%，IDLE 只剩 7–14%。与其猜哪个控件 贵，不如装两个计数器：交给面板的字节数，以及同样的像素按 32 行分带的直方图。 一屏是 153,600 字节，所以第一个数字可以直接换算成"每秒几屏"。

停掉 UI 定时器后 flush 计数是 0 B/s：没有任何重绘是为了自己。 分带直方图随即点名——频率与信息行占了每次重绘的 40%，因为代码只要状态序号变动 就重写这些标签，而 lv_label_set_text() 即使字符串一模一样也会让标签 失效。

修完这一步，flush 从 526 KB/s（3.5 屏/秒）降到 344 KB/s，taskLVGL 从 56–61% 降到 42%。再用对照实验切分剩下的部分：冻结瀑布得 36–39%，冻结频谱曲线 得 15–17%。曲线花掉 25 个 CPU 百分点，却只占四分之一的重绘 面积——LVGL 是按抗锯齿线段计费的，不是按像素，而 240 个顶点的折线有 239 段。 改成每 2 列一个顶点：线宽不变、重绘面积不变，taskLVGL 降到 28–30%。

内存：瀑布存成调色板索引

最大的一块 .bss 是瀑布——19,200 字节的 RGB565。改成每像素一字节的 256 项调色板索引后占 10,624 字节（含 LVGL 要求放在像素之前的那块调色板）。稳态 free 从 48 升到 57–59 KB，最大连续块从 27–42 升到 38–48 KB，代价是混合时逐像素 查表的 1–2 个 CPU 百分点。这颗芯片上连续块正是 TLS 握手需要的，这笔交易划算。

完全没有网络时的配网

机身上有一颗 NTAG213。它是被动标签：手机能读，MCU 看不见，板上也没有读卡器。 所以手机要把东西交给设备，唯一办法是让设备自己变成热点——当它没有任何凭据，或者 连续两次连接失败（间隔 30 秒）时就会这样做：SoftAP、DHCP 提供 192.168.4.1、一页 五个字段的表单，提交后重启进入 STA 模式。

设置存在 NVS 中并覆盖编译期默认值，所以配网过的设备不需要重新编译。而 Wi-Fi 驱动 每次开机都会写一条 NVS 记录，24 KB 分区最终会满：保存路径会打印 NVS 统计，失败时 擦除并重试一次——配网正是唯一可以安全擦除的时刻。

那颗旋钮到底控制什么

OK 双击循环六档——频率、频道、步进、滤波、音量、麦克风增益—— 方向键只改当前档位的值。它们一度分担过这件事：方向键双击轮转电台组，听起来合理， 直到你想起扫频本身就是连续点按同一颗键。实测双击的 按下→按下间隔是 250–420 ms，与两次调频点按完全同一区间， 无法可靠区分。切档因此全部回到 OK。

滤波那个旋钮有个更隐蔽的毛病：它什么都不做。服务端可写的字段是 filter_width——电台按模式分组的档位索引；filter_hz 是由它算出的只读值，所以直接发频率等于静默丢弃。而且阶梯按模式分组： voice（SSB/AM/FM）与 narrow（CW/RTTY/DATA）的索引并不通用， 固件因此按当前模式选表。协议层已验证： filter_width=13 → filter_hz=2400、17 → 2700、 20 → 3000。

两个网络不够用

一台常年在包里的终端需要不止一个网络。现在它记三个，开机扫描后在它们之间选择—— 优先选上次成功拿到 IP 的那个，因为信号强度并不等于质量：有一次它挑了更响的 AP （−25 对 −27 dBm），结果落在了一个正在丢 10% 包的网络上。

这引出了有用的部分：esp_wifi 在热点以那种丢包率工作时从不报断开。 所以音频计数也参与投票：连续两分钟丢帧超过 2% 或欠载超过 50 次/秒，就重新扫描并 切到另一个可见候选——高铁上实测，从一个拥塞热点换到手机热点后，丢帧从 +200/分钟 变成 0，写入帧率从 1.9–26 变成 44–47 帧/秒。

剩下的是物理限制

在同一条移动蜂窝链路上，实测丢包 6.5–12%，RTT 峰值 6–10 秒。没有任何环形缓冲能 覆盖十秒的空洞：那是 320 KB 音频，而全部 SRAM 只有 400 KB。所以目标从"连续"变成 "优雅降级"——断流超过一秒就丢弃已排队的音频而不是回放旧数据；环超过 75% 满时改为 丢最旧的帧而不是最新的，让恢复突发之后留下的是新音频。现在失败是安静的，而不是 剧烈的。
